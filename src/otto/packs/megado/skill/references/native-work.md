# The same Megado protocol in files and native work tools

Preserve six meanings in both modes: North Star, bounded goal, adopted configuration, plan, task structure, observed status. In the file bootstrap they live under one `.otto` control root and the adopted recorder. In native Otto/Herzchen use shared work/documents/revisions/metadata, not a private Megado database or a shadow tasklist.

Use a built-in blank project or an explicit task-structure template. Creation saves pending identity/content immediately. A correctly formatted but unfilled pending plan is valid to retain; it is not admission to execute. The manager adds outcomes, relevant documents, custom fields, prerequisites and criteria in one editable sheet. Actual sessions, accepted decisions and consumed resources remain generated/protected records. XHARD is schema-validated metadata whose meaning the manager interprets; finite profile lookup is not policy reasoning.

One edit token per canonical scope and actor. Read-only context and actual result appends continue. Manual or idle finish saves the final bytes, validates the authorised batch, closes and releases, then removes only registered disposable editing files. Save invalid input as a recoverable rejected draft; do not erase canonical project/content/history or files needed by running pack invocations. A shared document retains its own editing scope. Finish before asking a subordinate to claim a scope you hold.

A work task remains an outcome across attempts. The manager can correct, split, investigate, request an advisor or wait; no task-per-loop clone or automatic workflow language. An accepted approval identifies the candidate, criteria revision and permitted responsibility. Invoking a capability successfully does not close its enclosing task. Unknown feedback remains unknown.

The host uses canonical invoke/resume/send/inspect/cancel/wait where the actual adapter supports them. Actual actor, responsibility, session and invocation are different identities. Adopt an existing live session without launching a duplicate. Supported scheduled attention brings instructions to an accountable owner; neither elapsed time nor a new dependency result chooses business work automatically.

Use shared receipts/events and review/decision records. Preserve original IDs or explicit maps on adoption; cloning a template is not adoption of a live effort and never creates fresh shared allowance. Product source stays in Git; canonical control data stays with its owning service. Source manifests are documents, not a second live source repository.

The controller managing real work is a pinned installed build in a separate environment/realm from candidate code. Candidate tests cannot reset its database. Repairs and controlled upgrades preserve current state and uncertain external operations. Broad failure injection uses disposable replicas, not the only live ledger.

The application owns the invocation and review counters. Tests-only acceptance is allowed only by the adopted effort policy; linking a tests-only template cannot override a required advisor. A review result is immutable. An originally declared objective closure condition may be discharged by an independently observed bounded check and owner decision; a subjective or UNKNOWN result requires actual judgment, not a metadata change. Do not add per-protocol tables for this.

Begin from a derived resolved responsibility brief rather than repeatedly rebuilding context from unrelated files. Reuse canonical input/profile references and inspect only the needed detail. A manager can select a normal independent Luna Extra High review, a justified XHARD Sol High review, or no extra review when direct evidence suffices; chosen scopes/limits and independence still apply. The same domain operation serves direct commands and managed sheets. No private template scheduler, parallel authoritative summary or per-interface validation fork is required.

When a project-sheet batch returns both a containing project and child
changes, keep those identities separate. Use `SheetApplication.project.ref`
as the batch target and select the intended child from
`SheetApplication.mappings` by its typed `work.task` identity (or by a fresh
`WorkSheet.export(project_ref, task_refs=[child_ref])` read). A child revise
still commits through the containing project batch: its `base_revision` is
the current project revision, while the returned mapping supplies the new
child revision. Preserve prerequisite and document refs separately. Reject a
missing, wrong-kind, or stale selected ref before dispatch; do not infer the
child from the latest list entry. The runnable source-origin example and
receipt are retained at
`work/optimisation-boundary1-20260915/r2.2-child-selector-example.py` and
`r2.2-child-selector-proof.json`.

## Execution visibility from existing records

Use supported receipts, events, assignments, results and assessments to derive the current owner, last substantive result, next executable action, blocking prerequisite, attempts on the same outcome and applicable passing proof. Prefer a generated view over manually copied status or a second ledger. Correlate by stable task/assignment/attempt and relevant candidate/input identity; changed titles or decision IDs do not make a repair a new outcome.

Use recorded timestamps and lifecycle transitions for elapsed or waiting intervals. Tool activity alone does not prove useful progress; counts alone do not prove wasted work. Keep coordination, execution, external waiting and unknown intervals distinct where evidence allows, avoid double-counting concurrent work, and label missing telemetry unobserved rather than estimating it as fact. Where a supported view is absent, link available records and name the gap; this guidance does not claim an automatic diagnostic is installed.

At an existing manager check, surface actionable patterns such as repeated handoffs without a new result, a local correction waiting for unnecessary permission, or duplicated verification of unchanged inputs. The manager chooses a concrete continuation or correction under the mandate. No new polling schedule, automatic authority change, score per edit, review stage or required narrative report is introduced.

## Implemented process improvement

For any adopted improvement check, use [review-to-action](improvement-loop.md). The manager edits the canonical plan, delegates corrections and records observed effects through existing work/document/assignment tools. A schedule never sets its own business priorities, but its accountable orchestrator is expected to act. Reuse the existing report and task history; a separate improvement engine or review cadence is not implied.

## Current correction dispatch

Correction work uses the existing bounded brief and launcher. The brief must select
the active run explicitly and carry one role-labelled candidate manifest, task and
assignment/reporting route, controller pointer when applicable, exact observable
and expected result, owned write roots/interpreter, adopted resource revision,
latest result, unresolved attention and the next supported action. Validate these bindings at assignment or a material handoff and refresh only
affected references. A missing run, owned scope or relevant binding must be
resolved before dependent work; routine edits and focused tests reuse the current
assignment. The project seed is not an implicit substitute. Historical and current source
roles remain separate, and requested model/profile is not execution telemetry.

Before any install or test mutation, use the owned-root launcher with an absolute
disposable root, install target and interpreter. It resolves each path, refuses
outside-root and symlink escapes, and checks command path flags before starting
the child. Keep the external controller environment and protected sources out of
the owned root. Record the launcher command, resolved paths, actual interpreter,
brief/resource digests, communication route and result in the returned receipt.
