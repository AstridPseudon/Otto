# ASTRID-ON-FLEET study

## Agent flow and fleet gaps

The names overlap, but the execution units do not. Astrid's `GenericPackHost` is a host for discovered pack capabilities: it claims queued Runtime work, then runs a task carrying an `attempt_id` and `fence` (`Astrid/astrid/core/execution/generic_host.py:5044`, `:8511`, `:9871`). Its public SDK invokes a selected capability with inputs and execution/idempotency context (`Astrid/astrid/sdk/invocation.py:3945`). An Astrid capability execution, such as a render or executor, is media/workflow execution; it is not inherently an LLM agent turn. A parent orchestrator is explicitly a local launcher whose child executor calls use Runtime, rather than a Runtime executor registration (`Astrid/astrid/sdk/invocation.py:463`).

## Ledger and receipts

Astrid's command identity is a semantic request identity: `request_hash` hashes the command kind and canonical request after generated fields are removed, while the idempotency key is matched separately (`Astrid/astrid/core/receipts/canonical.py:222-243`). Its immutable command receipt DTO requires exactly nine fields: receipt ID, command kind, idempotency key, request hash, project ID, project sequence range, event IDs, result, and creation time (`Astrid/astrid/core/receipts/contract.py:15-27`, `:40-52`, `:96-119`). The SDK's remote adapter parses a returned receipt alongside `data` and exposes it through `DomainResult` (`Astrid/astrid/sdk/remote.py:425-431`). Astrid's environment documentation explicitly assigns ownership of durable receipts, events, and execution state to the Banodoco workspace Runtime, and says Astrid does not open a local database/CAS (`Astrid/docs/reference/env-vars.md:7-9`). The CLI contract describes a committed mutation receipt and says the idempotency key is caller-supplied or generated by the SDK before mutation (`Astrid/docs/contracts/cli-contract.md:38-66`). The physical persistence implementation and retention duration remain unverified from the supplied sources.

The execution reconciler has another kind of receipt: `_receipts` is a list cleared at the start of each `run`, and the result is assembled from that list (`Astrid/astrid/core/execution/reconciler.py:292-317`, `:455-468`). It reads a task through a Runtime facade and validates returned task, idempotency key, capability, and stored execution request identity (`:350-403`). A terminal Runtime task can supply durable result evidence, while a succeeded task without a recoverable result is reported as `undetermined` (`:405-453`). This separates Runtime's durable task state from the reconciler's process-local trace; the trace itself is not shown as a durable ledger.

The reconciler distinguishes safe-to-retry conditions from uncertain execution. For example, a target preflight failure and a queue deadline can return `retryable` before a task is executing (`Astrid/astrid/core/execution/reconciler.py:480-493`), but after admission it checks durable task state and refuses replay when a task is already in flight (`:516-581`). Later execution and settlement paths can instead return `undetermined` when settlement or durable recovery cannot establish an outcome (`:770-793`). Command-level idempotency makes a repeated semantic mutation recognizable by its key and request hash; it does not by itself establish at-most-once execution of a media effect, or resolve an unknown task outcome. The reconciler's task identity checks and refusal to replay in-flight work address a distinct execution boundary. A known retryable condition therefore does not mean an unknown effect may be replayed. The available code does not establish that Astrid and Otto share a reconciliation ledger or converge automatically.

Otto Runner keys one command by a caller `run_id` plus a binding over argv, cwd, and commit; reusing the ID with a different binding is rejected, while a matching ID returns the existing state without launching again (`src/herzchen/fleet/runner/runner.py:78-101`). Its `ResultStore` writes sealed records under `runs/`, verifies the seal and binding on reads, and disallows overwriting terminal `settled` or `unknown` records (`src/herzchen/fleet/runner/store.py:1-20`, `:31-36`, `:77-100`, `:150-177`). Runner's ledger is therefore persisted in its configured store; the cited implementation does not specify an expiry or retention policy, so retention duration is unverified. `src/otto/host_bridge.py:78-120` describes a separate finite, owner-approved host effect request with a configuration fingerprint and idempotency key; it is an adapter contract, not evidence that the effect itself or its receipts are durably retained there.

The planned EFFECTS project calls for “one effect ledger in Herzchen: at most once per identity, unknown held, one reconciliation,” with per-case capture and recovery modules identified for deletion (`/Users/hannahomalley/Developer/otto-program/PLAN.md:333`). This is a plan statement, not a present implementation contract: identity scope, receipt fields, storage authority, retention, and reconciliation behavior for EFFECTS are not specified at that line. Against that plan, Astrid's request-hash plus separate idempotency-key model and Runtime task authority are useful comparison points; Otto Runner's command binding and sealed run records cover a narrower heavy-command case. The evidence supports comparison, not convergence or a safe deletion of either system's receipt paths.

**Measured deletion budget for ledger/receipt comparison: 0 lines.** No candidate duplicate has been shown removable: Astrid's command receipt persistence/retention owner is unverified, the reconciler trace has per-run and durable-evidence roles, and Otto Runner's record store is its current command evidence. No pytest applies to this study task; focused acceptance is the section check plus citation, retention, and diff review.

## Cold agent UX walkthrough

### Cold brief and count

I treated the proposed route above as the input given to a new film-edit agent: “An agent turn on the Herzchen fleet asks an owner to admit an Astrid capability execution. Astrid retains capability readiness, attempt fencing, media input/output custody; Herzchen supplies role/capacity selection, workspace, turn host and tools. The owner boundary between admissions is not an existing integration.” That paragraph has **0 agent-directed verbs, 0 named agent tools, and 0 actionable steps**: it describes responsibilities but never tells the agent what to call, what to return, or what to do on refusal. The nouns “owner”, “capability”, and “fleet” leave the agent to invent the handoff.

For the compact brief paragraph below (excluding the numbered elaboration), I count **5 unique agent-facing verbs** (use, invoke, follow, stop, return) and **1 logical tool**; its numbered elaboration has **3 steps**:

> Use the fleet capability-request tool with a capability ID and its declared inputs. Do not invoke Astrid Runtime directly. If refused, follow `next_action`; if pending or unknown, stop and return the request reference without retrying. Return the result and request reference to your caller.
>
> 1. Read the task and allowed capability from your assignment.
> 2. Request one capability through the fleet owner.
> 3. Follow the returned recovery instruction or return the result/reference.

This brief describes **one proposed logical `request_astrid_capability` tool**, not a tool currently present under that name. The fleet facade lists tools by the worker token’s role (`src/herzchen/fleet/tools/facade.py:157-167`), and a call derives its assignment from that token and forwards the allowlisted operation to the owner (`:169-194`). The actual `ToolSpec` set is assembled by callers; this study has not found an Astrid capability tool or a mapping from its result to a fleet assignment. The current study’s proposed route therefore cannot yet be followed by an agent using only existing fleet tools.

### Handoffs, refusals, and request identity

The fleet dispatcher builds and validates the owner-decided `TurnSpec`, reserves a host turn, rechecks admission/readiness immediately before launch, and marks post-launch exceptions `unknown` so authority and capacity remain held (`src/herzchen/fleet/dispatch.py:117-158`). This gives the fleet a clear agent-turn boundary. The existing worker facade then passes only `operation`, token-derived `assignment`, validated args, and feedback status to its owner (`src/herzchen/fleet/tools/facade.py:169-194`). No cited fleet path admits an Astrid capability or carries the attempt/fence identity from the study’s Astrid side into that call.

Current fleet tool refusals are not directly actionable for an agent: unauthorized, forbidden, malformed-argument, and owner failures are shaped as `ok: false`, `error`, and `detail`, without `next_action` (`src/herzchen/fleet/tools/facade.py:96-98`, `:157-188`, `:218-230`). The socket server’s malformed-request and internal-error responses use the same shape (`src/herzchen/fleet/tools/server.py:21-27`, `:30-60`). Otto does have a separate retained-request timeout response with a `next_action` that names `request-status` and says not to resend (`src/otto/hostctl/lanes.py:112-126`), so the shape exists elsewhere but is not the worker-tool refusal contract. In Astrid, the SDK’s frozen error object has only `code`, `message`, and `details` (`Astrid/astrid/sdk/contracts.py:80-112`); the CLI contract says JSON returns that error envelope and directs agents to parse `recovery:` from stderr as the canonical next command (`Astrid/docs/contracts/cli-contract.md:60-70`). A Runtime startup failure also emits a `next_action` field (`Astrid/astrid/runtime_cli.py:418-425`). These are useful but distinct conventions; an adapter must normalize them into one tool result with a typed next action and an explicit unknown/pending state.

Request-key ownership is another unimplemented seam. Fleet `ToolFacade` validates declared argument names and forwards those arguments, but it does not mint or attach a request key (`src/herzchen/fleet/tools/facade.py:181-194`). Otto’s `HostEffect` requires a supplied `idempotency_key` and defines it as stable for one logical operation (`src/otto/host_bridge.py:74-95`); its bridge rejects reuse with a changed effect and replays or reads back by that key (`:355-390`), but the bridge keeps `_receipts` on the bridge instance (`src/otto/host_bridge.py:328`, `:355-367`). Astrid’s SDK accepts an optional idempotency key on capability invocation (`Astrid/astrid/sdk/invocation.py:3945-3960`), while its CLI contract assigns the key to the caller or to the SDK before mutation (`Astrid/docs/contracts/cli-contract.md:60-66`); the timeline CLI shows that concrete choice (`Astrid/astrid/packs/timeline/cli.py:130-136`, `:2955-2976`). So “the owner supplies a stable request reference” in the compact brief is a recommendation for the integration, not existing fleet behavior. To meet the program rule that tools mint request keys, the owner-side capability tool should mint/bind the key to the admitted assignment and semantic capability request, then return it on success, refusal, pending, and unknown results. The agent should not invent or change it during retry.

The most confusing proposed handoff is “agent asks owner to admit capability”: the current fleet owner operation is opaque to the worker, while Astrid `invoke` is a public SDK entry that accepts capability ID, inputs, execution context and optional key, then invokes through Runtime or an installed host bridge (`Astrid/astrid/sdk/invocation.py:3945-3989`). Without a single named fleet tool and a response contract, a cold agent may call Astrid directly, lose the fleet assignment and tool authority context, and make retries under a different key. The shorter brief above removes that choice only once the proposed owner tool exists.

### UX recommendation and cleanup budget

Implement one owner-mediated capability request tool with a small input schema (capability ID plus declared inputs), owner-minted stable request key, and a common result/refusal envelope containing `next_action` and an explicit pending/unknown state. Keep the fleet assignment/token implicit as it is today, and keep Runtime credentials and raw Astrid invocation out of the agent’s tools. Put the retry rule in the tool contract so the brief can remain three steps. These are recommendations, not claims about a current integration.

**Measured deletion budget for this UX walkthrough: 0 lines.** I found no safe redundant step to delete: fleet dispatch performs admission and prelaunch checks; the later Astrid capability admission is a separate boundary with no existing bridge. A future implementation could test whether it has duplicated reads after defining ownership, but present evidence does not justify removing either check. No pytest applies to this read-only study task. Focused acceptance is the section-heading check, citation verification, and `git diff --check`.

## Decision and follow-up

### Decisions

**Run Astrid film-edit agents as Herzchen fleet turns: yes, conditionally, after a bounded integration project.** The route fits the existing boundaries: Herzchen can own assignment-scoped agent turns and tools (`src/herzchen/fleet/hosts/contract.py:123`, `src/herzchen/fleet/tools/facade.py:157-194`), while Astrid continues to own capability readiness, attempt/fence identity, and media execution (`Astrid/astrid/core/execution/generic_host.py:8511`, `:9871`; `Astrid/astrid/sdk/invocation.py:3945-3989`). This is a design recommendation, not a claim that dispatch integration exists. The agent must request a capability through one owner-mediated tool; it must not receive Runtime credentials or invoke Runtime directly. The owner must bind the request to the assignment and a stable key, preserve Astrid's attempt/fence identity, and return a reference plus actionable `next_action` on refusal, pending, or unknown outcomes. The reconciler must not replay an in-flight or unknown effect (`Astrid/astrid/core/execution/reconciler.py:516-581`, `:770-793`). These are acceptance invariants for follow-up, not demonstrated behavior of a current bridge.

The alternatives are to keep film-edit agents outside this fleet, which avoids a new cross-owner boundary but forgoes fleet turn/tool admission; or to expose Astrid capabilities directly to agents, which the evidence does not support because it loses the assignment-mediated authority and retry contract described above. A capability execution is not itself an agent turn (`Astrid/astrid/sdk/invocation.py:463`, `:3945`), so the fleet must not represent one as the other.

**Merge Astrid Runtime's idempotency ledger with planned EFFECTS: no, on present evidence.** Keep Astrid command receipts/task state and Otto's planned effect ledger as distinct authorities until EFFECTS defines identity scope, receipt contract, persistence authority, retention, and unknown-outcome reconciliation. Astrid's receipt contract and Runtime ownership are evidenced (`Astrid/astrid/core/receipts/contract.py:40-52`; `Astrid/docs/reference/env-vars.md:7-9`), but the physical persistence implementation and retention are not. EFFECTS is currently described only as “one effect ledger in Herzchen” with “at most once per identity, unknown held, one reconciliation” (`/Users/hannahomalley/Developer/otto-program/PLAN.md:333`); that does not specify whether Astrid Runtime receipts can serve that purpose. A semantic command key/hash does not prove at-most-once media effects, and a ledger merge must never authorize replay when the effect outcome is unknown (`Astrid/astrid/core/execution/reconciler.py:405-453`, `:516-581`).

The viable alternatives are an adapter that references the Astrid receipt/task identity from EFFECTS while preserving Runtime as authority, or a later shared ledger only if both owners agree on identity, retention, reconciliation and migration semantics. The first is the safer starting hypothesis; neither is evidenced as implemented. Do not delete either receipt path on this study's evidence.
