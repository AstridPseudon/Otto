## Thin path: what it provides

Astrid has a working, git-native execution loop around project managers: the manager owns its queue, dispatches workers, reviews their changes and requests landings. The dispatcher starts workers and handles worktree, sync, land, CI and status requests outside the manager sandbox. It caps workers, records liveness and exit markers, and polls for requests every 20 seconds. That is a concrete path for parallel, multi-repo product work without making the dispatcher choose tasks. [Astrid `MANAGER-CODEX.md:64–77`](</home/user/repo/astrid-install/MANAGER-CODEX.md:64>), [`tools/dispatcher.sh:16–18, 42–54, 85–96`](</home/user/repo/astrid-install/tools/dispatcher.sh:16>)

Managers are instructed to work back to back, check worker results, run tests and land through the dispatcher; manager cycles produce summaries, and the orchestrator checks in hourly. The digests show this loop being used: a manager reports queue and landing state at turn end, and starts newly unblocked tasks while other work runs. [Astrid `MANAGER-CODEX.md:64–77, 114–124`](</home/user/repo/astrid-install/MANAGER-CODEX.md:64>), [`../data/mgr1-digest.txt:143, 333, 548`](</tmp/claude-0/-home-user/61c0e870-3601-52f0-903b-3607ce5e0548/scratchpad/retro/data/mgr1-digest.txt:143>)

**Otto’s canon has analogous labs, landing and runner code**, but the Astrid scripts are already shaped around Astrid’s branches, multi-repo worktrees, CI and queues. That is the main evidence-based operational gap—not proof that Otto’s underlying mechanisms are absent. ## What Otto has that the thin path lacks

Otto’s owner service is designed to hold one Store and bind admitted hosts, principals, projects and manager commands. The host guide says clients work through their own lanes; a host does not open the Store or start a second owner. [Otto `docs/host-onboarding.md:3–12, 25–35`](</tmp/claude-0/-home-user/61c0e870-3601-52f0-903b-3607ce5e0548/scratchpad/otto/otto/docs/host-onboarding.md:3>)

Otto also has mechanisms the Astrid file workflow implements only partially or manually: process custody and recovery; assignment and authority fences; receipt-backed launch, landing and evidence; and completion gates. The paused-state notes describe those protections, while also listing incomplete fixes and integration work. [`../otto/FIXES-ESSENCE.md:7–18`](</tmp/claude-0/-home-user/61c0e870-3601-52f0-903b-3607ce5e0548/scratchpad/otto/FIXES-ESSENCE.md:7>)

## Pilot additions for the target

The proposed pilot is explicitly the thin path: git/files, an observation-mode stop hook, message files and a supervisor sweep, measured for a week. [Retro `07-first-principles-review.md:68–72`](</home/user/repo/astrid-install/retro/07-first-principles-review.md:68>)

- **Turn-exit hook:** Record each manager exit as `working` with named runs and expected times, `blocked` with escalation sent, `done` with evidence, or `handoff`. Start in observation mode. The target calls for nudging the manager on the first mismatch and escalating a repeat to its supervisor. [Retro `07-first-principles-review.md:42–45`](</home/user/repo/astrid-install/retro/07-first-principles-review.md:42>)
- **Message files:** Add a shared, durable message format with id, sender, recipient, task, kind, needs-reply and resolved state, plus a wake-up path. Escalation should be tied to repetition or an unanswered reply past its deadline. Existing `ESCALATE.md`/approval files are ad hoc examples, not this complete interface. [Astrid `MANAGER-CODEX.md:29, 36`](</home/user/repo/astrid-install/MANAGER-CODEX.md:29>); [Retro `07-first-principles-review.md:49`](</home/user/repo/astrid-install/retro/07-first-principles-review.md:49>)
- **Supervisor sweep:** Add a cheap hourly pass over manager exit declarations, queues, run records and worker liveness. It should nudge managers directly and send exceptions to the orchestrator; it must not dispatch work or integrate code. [Retro `07-first-principles-review.md:50`](</home/user/repo/astrid-install/retro/07-first-principles-review.md:50>)

**Inference:** Treat existing Astrid dispatcher markers and run files as inputs to those checks. The target also calls for receipts authored by the tools, so the pilot should preserve each dispatch/check/land result with its base and execution identity, rather than treating hand-maintained queue state as proof. [Retro `07-first-principles-review.md:47`](</home/user/repo/astrid-install/retro/07-first-principles-review.md:47>)

## Can Otto code be reused without Otto’s owner service?

**Yes, with adapter work; it is not a drop-in Astrid integration.** Otto packages `src/` as `otto-herzchen` with no declared runtime dependencies. Its lower-level fleet modules are importable: `LabFleet` takes a repo, labs directory and checkpoint callback; `Runner` takes a capacity pool and result store; `LandingService` takes injected fleet, runner, task lookup and owner-supplied assessment/completion/result predicates. [`otto/pyproject.toml:5–20`](</tmp/claude-0/-home-user/61c0e870-3601-52f0-903b-3607ce5e0548/scratchpad/otto/otto/pyproject.toml:5>); [`src/herzchen/fleet/labs.py:256–273`](</tmp/claude-0/-home-user/61c0e870-3601-52f0-903b-3607ce5e0548/scratchpad/otto/otto/src/herzchen/fleet/labs.py:256>); [`runner/runner.py:43–59`](</tmp/claude-0/-home-user/61c0e870-3601-52f0-903b-3607ce5e0548/scratchpad/otto/otto/src/herzchen/fleet/runner/runner.py:43>); [`landing.py:62–94`](</tmp/claude-0/-home-user/61c0e870-3601-52f0-903b-3607ce5e0548/scratchpad/otto/otto/src/herzchen/fleet/landing.py:62>)

The runner can be embedded as Python objects or run as its own daemon; that daemon is separate from Otto’s owner service. Landing is the more coupled piece: a thin-path pilot must supply its own admission, assessment, completion-gate and sealed-result callbacks. [Otto `src/herzchen/fleet/runner/server.py:132–156`](</tmp/claude-0/-home-user/61c0e870-3601-52f0-903b-3607ce5e0548/scratchpad/otto/otto/src/herzchen/fleet/runner/server.py:132>); [`landing.py:65–80, 105–114`](</tmp/claude-0/-home-user/61c0e870-3601-52f0-903b-3601-52f0-903b-3607ce5e0548/scratchpad/otto/otto/src/herzchen/fleet/landing.py:65>) (path as cited: [`landing.py:65`](</tmp/claude-0/-home-user/61c0e870-3601-52f0-903b-3601-52f0-903b-3607ce5e0548/scratchpad/otto/otto/src/herzchen/fleet/landing.py:65>))

**Inference:** A sensible pilot could reuse `LabFleet` and `Runner` first, then add an Astrid-specific adapter for landing and receipts.
