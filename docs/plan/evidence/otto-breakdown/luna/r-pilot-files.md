### Windows PowerShell 5.1 runner

The acceptance journey must run on a real Windows runner and cover fresh install, stale-setting update, reinstall, authorized `/agents` and `/models` discovery without provider credentials, Runtime identity, capability readiness, and a negative control that breaks the model command. [plans/FIX-windows-install-findings.md:81–93](../astrid-plan-repo/plans/FIX-windows-install-findings.md:81)

The revised CI plan specifies product-repo GitHub Actions, a **pinned Windows Server image** (not floating `windows-latest`), a frozen tuple of Agent/Runtime/App/Pinokio commits plus manifest/artifact hashes, and explicit cross-repo read access. Its earlier roadmap says prove Windows access before the pilot; if hosted jobs remain queued, a self-hosted Windows runner is the stated fallback. [plans/TEST-cross-platform-testing.md:148–180](../astrid-plan-repo/plans/TEST-cross-platform-testing.md:148) [retro/08-otto-roadmap.md:56](../retro/08-otto-roadmap.md:56)

**Dependency distinction:** W1 is the explicit row that must include the updater path; W6 is explicitly an updater recovery behavior and depends on the rebased updater work in practice. W2–W5 and COH-C14 can be worked from current product `main`/the rebased integration line, but release qualification must run against the frozen integrated candidate tuple, not silently fall back to `main`.
