## Assessment

The branches contain useful, tested parts, but none is a ready-made implementation of the minimal tool end to end. The strongest transfers are Megado’s pack resources, bounded project-folder editing semantics, the consolidated CLI/status work, and focused worker feedback checks. These generally need adaptation around Otto’s owner service, custom Store, and authority model.

Test counts below are **recorded in each branch’s `.project/PROJECT.md`**, not tests rerun for this investigation. “No recorded pass” means the test file exists or a task describes an acceptance check, but I found no passing result recorded for it in the branch log.

## Cross-cutting components

- **Spec-folder sync:** Otto has a concrete implementation in `project_folder.py` (`export_project_folder`, `import_project_folder`, `finish_project_folder`, `release_project_folder`) and CLI folder open/check-in/release paths (`projects/packs/src/otto/portfolio/project_folder.py:220-322`; `.../cli.py:126-132,1379-1436`). Session state records a base revision and checks actor/session identity (`.../project_folder.py:271-304`); `show.py` preflights stale check-ins (`.../show.py:66-103`). Relevant test files exist: `test_document_sessions.py`, `test_document_failures.py`, and `test_project_onboarding.py` (`.../src/otto/portfolio/tests/`). **Passing evidence:** I found no branch `.project` result recording these tests passing. **Coupling:** high; folder flow calls authoring sessions and content operations, and `project_folder.py` verifies retained checkout identity. **Verdict:** adapt the check-out/check-in and stale-base semantics; rewrite the storage boundary for plain SQLite. **Inference:** the current code’s owner/session abstractions make direct extraction costly.

- **Tasks:** The packs project describes task extensions/templates, while throughput tests worker `check` separately from accepted `done` (`projects/packs/.project/tasklist.md:10,12`; `projects/throughput/.project/tasklist.md:9`). **Passing evidence:** pack-template and landing results above. **Coupling:** task rows and completion currently sit in Otto work sheets and admission/landing flows. **Verdict:** adapt task fields and acceptance separation, not the work-sheet implementation.

- **Messages and wake-up:** slim preserves DueRecord wake/delivery while consolidating direction composition (`projects/slim/.project/tasklist.md:13`; `.../.project/PROJECT.md:16,42-43`). Otto’s `inbox.py` is a projection, and `manager_handoff.py` explicitly has no owner, Store, scheduler, or persistence (`projects/packs/src/otto/portfolio/manager_handoff.py:3`). **Passing evidence:** the SL1 effective-brief test passed; broad delivery/invocation checks needed the gate. **Coupling:** high for actual delivery/wake, which is tied to owner, assignment, and schedule identities. **Verdict:** adapt message kinds and parent/child routing; don’t lift the owner delivery path wholesale.

- **Schedules:** Megado profile resources include `scheduled_checks`; the branch tested malformed schedule-policy validation (`test_host_neutral_defaults.py`, 23 passed/13 subtests: `projects/packs/.project/PROJECT.md:22`). That is configuration validation, not a reminder scheduler. **Verdict:** adapt the data shape; no minimal orchestrator reminder loop is evidenced as built here.

- **Turn-end check:** I found no branch implementation or passing test for the design’s “open tasks and nothing running” stop/turn-end check. **Verdict:** build this small hook separately.

- **Spawn/resume through a harness:** `session_resume.py` validates assignment generation, native session, and schedule identity (`projects/packs/src/herzchen/fleet/runner/session_resume.py:12-34`), but no branch log establishes it as a generic Pi spawn/resume path. Harness3’s real-host work is blocked (`projects/harness3/.project/tasklist.md:7-12`). **Verdict:** adapt only the exact-session binding idea; implement the single Pi harness path separately.

- **Status and landing/integration:** slim’s `show`/`status` and throughput’s focused `check` are the best tested surfaces (results above). Existing `schema.py` defines Otto Store tables such as `identities`, `command_receipts`, `events`, and `project_history` (`projects/packs/src/herzchen/kernel/schema.py:29-87,137`), not the proposed six-table schema. **Verdict:** lift command/test patterns; adapt to the six-table SQLite model. The branch evidence does not establish Turso sync or a minimal protocol implementation.
