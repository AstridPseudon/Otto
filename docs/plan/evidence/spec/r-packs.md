### Pack format

The current files named `pack.yaml` are **JSON-formatted manifests**, not YAML: examples have `schema_version`, `id`, `name`, `version`, and `resources` entries of `{path, kind}` ([`megado/pack.yaml`:1–15, 25–35](../otto/projects/packs/src/otto/packs/megado/pack.yaml); [`otto-roles/pack.yaml`:1–15](../otto/projects/packs/src/otto/packs/otto-roles/pack.yaml)). Megado’s manifest enumerates protocols, schema, skill references, scripts, and templates ([`megado/pack.yaml`:11–103](../otto/projects/packs/src/otto/packs/megado/pack.yaml)); Astrid and Engineering use the same basic resource-list pattern ([`astrid/pack.yaml`:1–16](../otto/projects/packs/src/otto/packs/astrid/pack.yaml), [`engineering/pack.yaml`:1–12](../otto/projects/packs/src/otto/packs/engineering/pack.yaml)).

The existing loader requires `pack.yaml` to be valid JSON, schema version 2, with matching ID, name, semantic version, and nonempty resource declarations ([`authoring.py`:752–780](../otto/projects/packs/src/herzchen/packs/authoring.py)). `role_context.py` then expects a managed `otto-roles` pack containing `roles.json` in schema `otto.role-pack.v1` and validates role-specific fields ([`role_context.py`:33–94](../otto/projects/packs/src/otto/portfolio/role_context.py)). That is coupled to the Otto/Herzchen loader and JSON role schema.

**Recommendation (inference): keep the `pack.yaml` filename and a small manifest concept, but do not keep the current loader schema as a requirement.** The target design already defines a new manifest purpose—role defaults, selected skills, and reminder schedule ([`12-minimal-design.md`:16–25](../retro/12-minimal-design.md)). A concise manifest can name pack/version, defaults, role files, skills, and schedule; carrying forward the old resource taxonomy, role JSON contract, and provenance checks would reintroduce the retired loader layer ([`12-minimal-design.md`:11, 84–94](../retro/12-minimal-design.md)).
