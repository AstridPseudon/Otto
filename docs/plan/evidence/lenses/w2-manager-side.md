## Lens: The manager’s perspective

The four manager ledgers are present: [mgr1](out/w1-mgr1.md), [mgr2](out/w1-mgr2.md), [mgr3](out/w1-mgr3.md), and [mgr4](out/w1-mgr4.md). I checked their main claims against the oldest-first manager digests and the relevant handoff briefs. The primary sources show two distinct setups: Claude managers worked directly with repos and workers; later Codex managers used a dispatcher, request files, and run folders.

### Findings

1. **Managers treated their brief as an operating contract, but it changed during execution.** Mgr1 began by restoring state and taking the queue as its source of truth. At 00:36, the orchestrator clarified the intended cadence: run ready tasks back to back, use parallel workers, and stop scheduling self-checks. Mgr1 cancelled its already-scheduled wake-up and switched to parallel dispatch. The Claude brief was updated to encode that process ([mgr1 digest, 00:23, 00:36](data/mgr1-digest.txt); [BRIEF-claude-manager.md](</home/user/repo/handoff-upd/BRIEF-claude-manager.md>)). **Observed:** instructions changed behavior when they were specific and made it into the current brief or queue rulings.

2. **Worker briefs were strongest when they constrained one task and specified evidence.** Mgr2’s area reviewers got diff summaries and relevant contract extracts; fix briefs named the repo, task, scope, and expected tests. Mgr4 similarly gave each rebase worker a focused row, worktree, test expectations, and explicit prohibitions on commits, pushes, and pin edits ([mgr2 digest, 02:56–02:57](data/mgr2-digest.txt); [mgr4 digest, 10:01](data/mgr4-digest.txt)). This matches the Codex instructions to quote only relevant plan/contract sections, give one or two tests, and require exact output ([CODEX.md](</home/user/repo/astrid-install/CODEX.md>)). **Observed:** the best briefs made both scope and the manager’s review job legible. They did not prevent wrong assumptions about checkouts, test baselines, or fixtures.

3. **Managers did substantial independent review; worker reports alone were not reliable evidence.** Mgr2 checked “pre-existing” claims against `upd-base` and found App failures the workers had misclassified; it also corrected a worker’s baseline claim before landing ([mgr2 digest, 03:05–03:07, 03:20–03:22](data/mgr2-digest.txt)). Mgr3 caught that its first Pinokio comparison used the sibling checkout on `main`, then reverted a test edit after the correct checkout passed 14/14 ([mgr3 digest, 05:03–05:22](data/mgr3-digest.txt)). Mgr4 initially considered two Pinokio failures environmental, then corrected that classification after reproducing them on UPD ([mgr4 digest, 15:18–15:27](data/mgr4-digest.txt)). **Observed:** independent verification caught real mistakes in both implementation and attribution.

4. **Managers kept the queue moving, but “between tasks” often meant waiting on long work and reconstructing status.** Mgr1 initially waited for a scheduled check-in; after correction, it worked on other rows while workers ran. Mgr3 spent over two hours monitoring final suites, and the orchestrator prompted it to inspect progress. Mgr4 used detached tests and log polling, but a waiter matched its own command, and its `pkill` killed the shell attempting the restart ([mgr1 digest, 00:26–00:37](data/mgr1-digest.txt); [mgr3 digest, 06:31–08:59](data/mgr3-digest.txt); [mgr4 digest, 10:15](data/mgr4-digest.txt)). **Inference:** asynchronous work improved throughput when tasks were independent, but the managers lacked a dependable compact view of worker and test liveness.

5. **Landing and reporting were explicit manager responsibilities, with useful checkpoints and recurring hazards.** The Claude brief required a snapshot after each landing and a pushed phase-boundary report ([BRIEF-claude-manager.md](</home/user/repo/handoff-upd/BRIEF-claude-manager.md>)); mgr1 followed that and reported its open review, elegance, and rebase phases at 02:52 ([mgr1 digest](data/mgr1-digest.txt)). Codex managers had a more formal dispatcher flow: workers leave changes uncommitted, managers test and prepare landing, and the orchestrator commits/merges ([CODEX.md](</home/user/repo/astrid-install/CODEX.md>)). Yet mgr2 moved `prog/upd` backward with an update-ref against the wrong checkout before catching and repairing it; mgr3 staged an orchestrator-owned queue by mistake; mgr4’s final report disclosed that 1,021 agent tests had hung and not run ([mgr2 digest, 03:04](data/mgr2-digest.txt); [mgr3 digest, 05:59](data/mgr3-digest.txt); [mgr4 digest, 20:22–20:38](data/mgr4-digest.txt)). **Observed:** checkpoints and caveats worked; safe branch ownership and complete verification did not happen automatically.

6. **The most useful brief instructions had visible behavioral effects.** Mgr1 changed cadence after the “back to back” ruling, stopped per-task Opus review after “check each result yourself,” switched Opus to design-only after the 01:29 correction, and adopted baseline comparison and summary-only output after later instructions ([mgr1 digest, 00:36–00:45, 01:29–01:35, 01:52–01:58](data/mgr1-digest.txt)). Mgr3 applied the “user-visible wording” ruling by reverting label changes and deferring text cleanup; mgr4 changed the merge method and pin policy to “merge, don’t replay” and “no repinning” ([mgr3 digest, 05:59–06:26](data/mgr3-digest.txt); [mgr4 digest, 10:00–10:01](data/mgr4-digest.txt)). **Observed:** task cadence, review role, test classification, merge strategy, and scope all changed in response.

### What worked

- **A queue and a landing protocol gave managers a usable control loop.** They kept task state current, reused available worker slots, and reported phase boundaries. The later Codex brief’s dispatcher files, run folders, `worker.alive`, and explicit state transitions made that loop more structured ([MANAGER-CODEX.md](</home/user/repo/astrid-install/MANAGER-CODEX.md>); [mgr4 digest, 10:01](data/mgr4-digest.txt)).
- **Scoped briefs and manager-run checks caught bad worker assumptions.** The managers checked diffs, reran focused tests, and compared baselines before landing, rather than treating “done” reports as proof ([mgr2 digest, 03:20–03:39](data/mgr2-digest.txt); [mgr3 digest, 05:22–05:28](data/mgr3-digest.txt)).
- **The process allowed evidence-based escalation.** Mgr1 escalated missing adapters and unclear caller behavior; mgr2 escalated the App lock break; mgr4 escalated rebase rulings, then recorded the rulings in the queue before execution ([mgr1 digest, 00:45–01:01](data/mgr1-digest.txt); [mgr2 digest, 03:06–03:10](data/mgr2-digest.txt); [mgr4 digest, 10:19](data/mgr4-digest.txt)).
- **Managers disclosed verification limits.** Mgr2 distinguished its passing kill-point tests from the timed-out full integration run; mgr4’s completion record called out the unrun tests ([mgr2 digest, 04:52–04:53](data/mgr2-digest.txt); [mgr4 digest, 20:22–20:38](data/mgr4-digest.txt)).

### What failed / friction

- **Task assumptions were not preflighted against actual repo and test state.** Mgr1 found a missing launcher adapter and a mismatch between the F1e brief and the actual caller/fixture. Mgr3 first tested the wrong Pinokio checkout. **Observed:** these issues were discovered after dispatch, not from a standard readiness check ([mgr1 digest, 00:45–01:01](data/mgr1-digest.txt); [mgr3 digest, 05:03–05:22](data/mgr3-digest.txt)).
- **Baseline labels were easy to get wrong.** Mgr2 and mgr3 found worker “pre-existing” claims that did not hold on the designated base; mgr4’s classification changed as the authority moved from UPD to `origin/main`, with new tests requiring separate treatment ([mgr2 digest, 03:20–03:22](data/mgr2-digest.txt); [mgr3 digest, 05:28](data/mgr3-digest.txt); [mgr4 digest, 13:04–15:27](data/mgr4-digest.txt)).
- **Repo and test mechanics created avoidable work.** Examples include missing worktree dependencies for X8, unsupported test flags, a wrong-branch ref update, brittle queue edits, and a deleted test log ([mgr1 digest, 00:43–00:44, 02:24](data/mgr1-digest.txt); [mgr2 digest, 03:04](data/mgr2-digest.txt); [mgr4 digest, 10:15, 20:17](data/mgr4-digest.txt)).
- **Long-running work lacked a reliable, concise status signal.** Managers polled logs and processes, waited through extended suites, and in the end still had hung or timed-out test work. The Codex docs define `worker.alive`, but the evidence shows test-run liveness and completion still needed manual checking ([MANAGER-CODEX.md](</home/user/repo/astrid-install/MANAGER-CODEX.md>); [mgr3 digest, 06:31–08:59](data/mgr3-digest.txt); [mgr4 digest, 20:22–20:38](data/mgr4-digest.txt)).

### Candidate principles

- **When a task depends on a repo state or caller path, require a preflight of branch, checkout, fixture, and relevant caller before dispatch, because managers discovered missing adapters and wrong checkouts only after work began** ([mgr1, 00:45–01:01](data/mgr1-digest.txt); [mgr3, 05:03–05:22](data/mgr3-digest.txt)).
- **When a worker reports a pass, failure, or “pre-existing” result, require the exact command, branch/commit, selected tests, and baseline evidence, because managers repeatedly overturned unsupported worker classifications** ([mgr2, 03:20–03:22](data/mgr2-digest.txt); [mgr3, 05:28](data/mgr3-digest.txt); [mgr4, 15:18–15:27](data/mgr4-digest.txt)).
- **When a task is independent and tests are running, keep the manager on startable work; use explicit dependencies to prevent premature dispatch, because back-to-back parallel work reduced idle time but dependent work blocked on F1d and R1/R2** ([mgr1, 00:36–00:40](data/mgr1-digest.txt); [mgr4, 10:26](data/mgr4-digest.txt)).
- **When a run is long, record process state, last log update, timeout, and completed/remaining test IDs in one status artifact, because polling loops were unreliable and suites ended timed out or hung** ([mgr4, 10:15, 20:22–20:38](data/mgr4-digest.txt)).
- **When responsibility changes or a phase ends, require a handoff record with landed SHAs, open rows, test evidence, and explicit “not run” items, because fresh managers repeatedly restored state and final reports had to clarify incomplete verification** ([mgr1, 00:23–00:27](data/mgr1-digest.txt); [mgr4, 20:22–20:38](data/mgr4-digest.txt)).

### Structure implications

- **Task entity:** include acceptance criteria, test command, expected caller/fixture, repo/branch, dependencies, tier, and escalation owner.
- **Dispatch artifact:** freeze the brief and record worker model, worktree, base SHA, permitted paths/actions, and required report fields.
- **Test-run entity:** record repo, branch/commit, command, markers/selection, environment, baseline commit, log path, start time, last output time, timeout, exit code, and IDs not run.
- **Landing checklist:** verify target branch and expected old SHA before merge/update; record focused checks, baseline comparison, diff scope, landed commit, and snapshot.
- **Manager status view:** show startable, blocked, and running tasks; worker heartbeat plus test-process/log heartbeat; next action and last update. Use a defined cadence for check-ins and make it respond to phase changes.
- **Handoff/completion record:** list landed SHAs, open or deferred rows, pass/fail/pre-existing/environmental/not-run counts, and the next manager’s first action.
- **Checklist question:** “What evidence would make this worker’s claim false?” This would have prompted the managers’ successful baseline, checkout, and negative-control checks.
