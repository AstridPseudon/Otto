## Lens: Rulings and decision-making

**Scope note:** I treated “every decision” as each material owner choice and orchestrator ruling that changed scope, design, sequencing, acceptance, or the manager’s authority—not every routine task approval. I checked ledger claims against `data/main-full.txt`, `data/user-messages.txt`, `data/plan-repo-gitlog.txt`, and the live plan and queue files. The ledgers were useful indexes, but sometimes described proposals as settled before the owner confirmed them.

### Findings

1. **The owner set the product and delivery boundaries; the orchestrator turned them into operating rules.** On 26 Oct the owner asked for convenient defaults without over-engineering, cross-platform support, and visible consent [10-26 00:54, `data/user-messages.txt`]. The orchestrator chose one resolved `Choices` object and a shared integration lifecycle [10-26 01:24; `data/main-full.txt` lines 459–460]. The owner later approved a simple Windows start shortcut [10-26 01:45], zip delivery rather than product pushes [10-26 01:52; 22:38], and an eventual release reply only after shipping [10-26 02:03]. **Reasoning style:** make the ordinary path easy, preserve consent and reversibility, and keep delivery under owner control. **Decision time:** generally same-minute iteration; the release reply timing took one correction. **Held:** these boundaries were codified in the goal and plan. **Friction:** the orchestrator first drafted the reply too early, then moved it to project completion after the owner clarified.

2. **The orchestrator resolved plan conflicts and external dependencies by narrowing or deferring the work.** It ruled the native Pinokio Stop/Quit veto out of UPD because it required upstream Pinokio behavior [10-27 06:22; `data/main-full.txt` lines 4199–4207]. It deferred C2c because its prerequisites belonged to paused installer tasks [10-27 10:54–10:56; lines 4355–4365]. During rebase planning, it chose one merge per repo instead of replaying commits and kept existing pins [10-28 09:58–10:21; `REBASE-COMPLETE.md`]. For the schema digest, it put both re-vendoring and old-digest compatibility at **release time**, not in the rebase [10-28 10:45; `data/main-full.txt` lines 7336–7346]. **Principle:** don’t build substitutes for work owned elsewhere; put a decision in the phase that owns it. **Decision time:** same check-in or shortly after escalation. **Held:** the queue and completion report reflect these boundaries.

3. **When implementation was blocked by missing work inside the approved scope, the orchestrator authorized it; when a proposed implementation duplicated or exceeded scope, it cut it.** It told the manager to build the missing local Update route and split it from the Settings adapter: “Build the route. It’s in scope” [10-28 00:46; `data/main-full.txt` lines 6080–6103]. It narrowed F1e to the actual TypeScript client and existing test path, rejecting a hand-rolled HTTP helper and an unrelated canary [10-28 00:57; lines 6135–6147]. It also rejected vendored fixture edits for F1e [10-28 01:00; ledger chunk 6]. After repeated stop-path review rounds, it merged the related tasks and said “Stop patching piecemeal,” favoring a single result contract [10-28 01:02; ledger chunk 6]. **Principle:** choose the smallest implementation that exercises the real caller and closes the behavior. **Decision time:** minutes after manager escalation. **Held:** these rulings were written into the queue and task notes.

4. **Pin and baseline rulings protected compatibility while distinguishing regressions from old failures.** The orchestrator kept the shipped Runtime pin in place and chose defensive parsing of an optional `release` field, rather than changing the pin or manually changing vendored types [10-28 03:10; `data/main-full.txt` / queue record]. For rebase qualification, it required comparing failures with the base; a test that cannot run on `main` because its API is new still counts as a regression if it fails on the rebased branch [10-28 13:04–15:29; `data/main-full.txt` lines 7724–7735]. It later accepted a test-setup-only repair conditionally: fixture/helper files only, assertions unchanged; otherwise revert and classify as a regression [10-28 20:21; lines 8954–8965]. **Principle:** preserve the stable release boundary; qualify behavior against a named baseline; accept test-only changes only when they do not weaken the test. **Held:** the final completion report applies these classifications, but records 1,021 hung tests as unrun (`REBASE-COMPLETE.md`).

5. **Review scope and “elegance” changed more than once; the owner’s corrections ultimately set the boundary.** The owner requested reviews and, for the TST plan, told the orchestrator to make judgment calls rather than mechanically apply Astra’s cuts; the orchestrator produced a three-layer, 17-task plan and left it unqueued [10-27 21:07–21:50; `PROGRAM.md` §7 / TST plan]. For UPD, the owner first requested an Opus elegance pass, then clarified that it should fix small and medium items but report structural or risky changes [10-27 22:00–22:20]. Later, after Opus had been used outside that boundary, the owner corrected that Opus was for final reviews and taste work, not ordinary implementation; the orchestrator changed the policy [10-28 01:29–01:40]. It also skipped a planned six-hour direction review after three recent Opus rounds had covered the same ground [10-28 05:51]. **Principle:** reviewers should produce bounded, actionable fixes; avoid duplicate review; reserve material contract or structure changes for a decision. **Reversal:** the Opus assignment expanded, then was narrowed by owner correction.

6. **The owner repeatedly changed the program’s operating boundary and cadence.** They paused the install/release program and authorized UPD off `main` [10-27 02:24–02:30; `STATUS.md`]. They explicitly kept TST planned but unqueued [10-27 21:07, 21:50; `PROGRAM.md` §4]. They set difficulty-based worker tiers, later changing the mapping as available models and costs changed [10-27 20:54–20:55; 10-28 02:07; `runs/QUEUE.md`]. They instructed the orchestrator to guide and unblock, while the manager coordinates and executes, then said to make decisions overnight without asking [10-28 02:08; `ORCHESTRATOR.md`]. Finally, the owner turned off hourly review [10-28 18:09; ledger chunk 8]. **Principle:** owner controls project priority, execution boundary, and cadence; orchestrator owns routine in-scope execution judgments. **Held:** pause, queue status, role, and trigger changes appear in the current plan files.

7. **Some decisions were made promptly but without an explicit owner answer.** When the owner asked how to speed UPD, the orchestrator asked about a proposed four-part change and applied it ten minutes later without a recorded intervening answer [10-27 12:01–12:11; ledger chunk 4]. Later the owner had explicitly granted autonomous decisions overnight [10-28 02:08], so autonomy itself was authorized, but the transcript does not show that earlier speed-up proposal being approved. **Observed:** it held operationally. **Inference:** this was probably within delegated execution authority, but the approval state was ambiguous. The owner also asked whether to make a reply or CI setup; those choices were eventually made as drafts or scratch infrastructure, with external publication still governed by owner instructions [10-26 01:52–02:01; `PROGRAM.md` §7].

8. **The clearest decision-process failure was not a wrong technical ruling but drift between ruling and source of truth.** At 10:19 the owner asked if the rebase plan was clear; the orchestrator found the plan still said “replay” and “repin,” contradicting its own 09:58 rulings [10-28 09:58–10:19; `data/main-full.txt` lines 7078–7106]. The manager had to reconcile the documents before proceeding. Later queue and completion records did carry rulings, but this mismatch shows that a decision made in chat is not operational until the canonical plan and task row are updated.

### What worked

- **The owner’s delegation boundary was unusually explicit.** “No more questions” and “the manager should be doing everything” became written operating rules in `ORCHESTRATOR.md` [10-28 02:08].
- **Rulings usually included a concrete implementation boundary and evidence rule.** The F1e ruling identified the real caller, test harness, excluded work, and unrun platform checks [10-28 00:57; `data/main-full.txt` lines 6135–6147].
- **Rebase decisions were converted into a coherent plan after a direct consistency check.** The discrepancy was found and corrected before further execution [10-28 10:19–10:21; `data/main-full.txt` lines 7083–7106].
- **Owner judgment calls did not simply defer to reviewer preferences.** Astra’s cuts were considered individually and organized into a coherent, unqueued plan [10-27 21:41; `data/main-full.txt` lines 5184–5195].

### What failed / friction

- **The orchestrator occasionally overstepped its own role.** Opus was used for implementation/design before the owner corrected the policy [10-28 01:29–01:40].
- **A proposal, a ruling, and owner approval were not always distinguishable.** The speed-up was applied without a recorded answer; TST recommendations initially remained pending owner approval, then were settled through later messages [10-27 12:01–12:11; 10-28 10:48–10:50].
- **The escalation boundary lacked a reliable “product decision vs technical ruling” test.** Decisions about the Update route, secret reuse, and pin stability were made by the orchestrator without asking the owner. They were consistent with written requirements, but the transcripts do not show a formal delegation rule explaining why those were in scope for orchestrator judgment.
- **Review activity could inflate scope before it reduced it.** UPD review rounds added machinery, then the elegance pass found about 850 lines to remove [10-27 12:11–12:25; ledger chunk 5]. Bounded rounds and deduplication helped later.

### Candidate principles

- When a manager is blocked on work explicitly required by the accepted plan, **authorize the smallest missing implementation and split it at a clear boundary**, because the Update route was ruled in-scope and divided into route and UI tasks [10-28 00:46].
- When a proposed fix relies on another project, owner, or upstream system, **defer it with an owner and follow-up location**, because C2c and the native Pinokio veto were moved out of UPD instead of built as substitutes [10-27 06:22; 10:27 10:56].
- When a task is about integration behavior, **test the real caller through its existing harness**, because a hand-built HTTP helper would test a copy of the behavior [10-28 00:57].
- When deciding whether a failure is new, **compare against a named base and treat a newly added failing test as a regression**, because the rebase ruling prevented “cannot run on main” from being mistaken for “pre-existing” [10-28 13:04–15:29].
- When a ruling changes the sequence, pin, scope, or acceptance bar, **write it into the canonical plan, queue, and task record before the next dispatch**, because the rebase plan retained obsolete “replay” and “repin” instructions until checked [10-28 10:19].
- When an owner explicitly delegates execution, **make routine in-plan decisions autonomously and reserve owner contact for product direction, external commitments, or unresolved blockers**, consistent with `ORCHESTRATOR.md` and the owner’s 02:08 instruction.
- When a review identifies large structural or contract changes, **report options and recommendation before implementation**, because the owner distinguished small cleanup from bigger “gremlins” [10-27 22:19].

### Structure implications

- Give each decision a durable **ruling record**: task/plan ID, timestamp, question, options considered, chosen option, rationale/principle, decider (owner/orchestrator/manager), whether approval was explicit or delegated, and follow-up.
- Store **decision state** explicitly: proposed, owner-needed, approved, rejected, deferred, superseded. Do not treat a review finding or assistant recommendation as an owner decision.
- Add a **scope boundary field**: in scope / another project / upstream / owner action; require a destination and owner for deferred items.
- Track **reversal/supersession** with a link to the later ruling and a short reason, as in the Opus policy changes and the changing hourly-review state.
- Make the canonical plan and queue reference the same ruling ID; add a pre-dispatch check for contradictions, especially around pinning, merge strategy, release timing, and test acceptance.
- Add a **decision cadence trigger**: check pending owner decisions at each scheduled review; if the owner has delegated autonomy or is unavailable, apply the documented fallback and log that it was used.
- Give reviewer findings a disposition field—accepted, partly accepted, rejected, deferred—with the orchestrator’s reason; this matches the TST cuts and conditional R8-F3 acceptance, and avoids opaque reviewer authority.
