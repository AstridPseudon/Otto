## Lens: Tooling, environment and friction

### Findings

1. **The dispatcher made Codex worker execution possible, but it had to stand in for missing sandbox capabilities.** Four initial worker tasks failed before reading anything: Codex workers launched inside another Codex sandbox could not run shell commands. A host-side `dispatcher.sh` then started workers from `dispatch.json`, and later handled `worktree.request`, `sync.request`, `land.request`, `status.request` and `ci.request` files. The manager could coordinate through files while the dispatcher performed host-side operations. The plan repo records the dispatcher’s introduction at 10-26 23:38; the script documents the nested sandbox socket failure and allowlists models, paths, repos and branches (`data/main-full.txt` [10-26 23:32–23:38]; `/home/user/repo/astrid-install/tools/dispatcher.sh`). **Impact:** the four failed launches delayed useful work until discovered; exact elapsed cost was not measured. The workaround then accumulated substantial bespoke machinery.

2. **The dispatcher’s worker state was initially unreliable.** Container restarts stopped workers and the dispatcher; one restart also lost a worker’s exit marker. Later, C1a was marked “lost” three times even though its output existed. The team added restart recovery, heartbeat files, a detached wrapper that records exit codes, and rules to distinguish completed output from dead work. Partial work was recoverable from the worktree, but the false “lost” states prompted investigation and re-dispatches. (`data/main-full.txt` [10-27 00:01, 01:26, 04:59–05:35]; `out/w1-chunk-4.md`) **Inference:** one shared lifecycle service that owns worker state would have avoided several rounds of custom liveness repair.

3. **Codex and Claude were not interchangeable execution environments.** Local Codex CLI required device sign-in; the first Astra run blocked on stdin, and a `pkill` attempt killed its own shell. A `< /dev/null` invocation rule was later documented. During a later model switch, the remote manager’s container lacked Codex installation/login; use required a credential in environment secrets and a new session to read it. Separately, a Codex usage limit stopped work until Nov 2, prompting a handoff to a Claude Haiku manager. (`data/main-full.txt` [10-26 01:15–01:17; 10-28 00:00, 10:31–10:44]; `out/w1-chunk-1.md`, `out/w1-chunk-5.md`, `out/w1-chunk-7.md`) **Impact:** work paused at 54 completed rows before the handoff; the transcript does not quantify the time spent on login or environment setup.

4. **The permission classifier blocked both risky and owner-authorized operations.** It refused sending unreleased code bundles to a public repo as `[Data Exfiltration]`; making the repo private allowed that handoff push. Later, it still refused product-code pushes to the private CI repo. Writing the session’s own permission settings was refused as `[Self-Modification]`. The owner switched modes and approved a push; the dispatcher’s CI request path then worked. Earlier GitHub integration calls also returned 403 for repo creation and Actions access. (`data/main-full.txt` [10-26 01:55–01:58; 10-28 00:16–00:23, 15:50–15:53]; `out/w1-chunk-1.md`, `out/w1-chunk-6.md`, `out/w1-chunk-7.md`) **Impact:** pushes and CI setup stalled pending owner action. **What worked:** the assistant reported refusals and did not route around them; the owner changed the repo or approval setup, then the work proceeded. However, the later Actions smoke workflow remained queued across Linux, Windows and macOS after pushes succeeded [10-28 16:00–16:02].

5. **Auth and secret handling needed manual coordination.** Codex CLI used device authorization; the remote Codex environment needed an API key or configured secret, and only sessions started after configuration could see it. The handoff exporter scanned for secret-like strings and allowlisted known fake test values. A known fake key also appeared in a zip scan and was identified as a fixture, not a credential. (`data/main-full.txt` [10-26 01:15; 10-28 00:16, 10:32–10:44, 16:36]; `/home/user/repo/handoff-upd/export.sh`) The code-signing certificate was a separate real-world identity and account dependency, not something the agent could provision [10-26 01:02–01:04].

6. **Context compaction and manager restarts reduced cost at phase boundaries, but oversized context was expensive.** The manager reached 263K tokens, then 281K; the orchestrator attributed repeated reads to a major cost driver. It moved test output to files, asked for verdicts and failing names rather than full logs, and planned fresh managers at phase boundaries. A Codex usage cap also forced a cross-tool handoff. (`data/main-full.txt` [10-28 00:00, 01:57–01:58, 03:57]; `out/w1-chunk-5.md`, `out/w1-chunk-6.md`) **Impact:** the recorded spend was $16.05 for the old manager and about $59 across three sessions after handoff; these are transcript totals, not an isolated estimate of compaction overhead. Compaction summaries preserved broad state, but raw transcript access was still needed for exact details.

7. **Snapshots and repo boundaries protected work, but stale exports obscured current state.** The planning folder was first moved into git because its original location was not durable. Later snapshots preserved branch bundles and run records, but one lacked cleanup rows and already-landed work; another had not been pushed since 14:17 when checked at 16:02. The manager was told to export after each landing. (`data/main-full.txt` [10-26 20:02–20:10; 10-28 05:58, 16:02]; `data/plan-repo-gitlog.txt` [10-26 23:38; 10-28 16:02]) **Impact:** progress was harder to inspect and required nudges. The supplied raw transcript supports lost exit markers and stale snapshots, but I did not find evidence of product patches being lost because a folder was removed. It reports partial work still on disk after restarts [10-27 00:01].

8. **Keepalive and scheduled checks did not guarantee continuous execution.** Container reclaim stopped workers, keepalive and dispatcher; `/loop` scheduling was not durable across reclaim, and a job expected at 14:56 was absent. Choosing check-in-only operation meant only about 5–10 minutes of runtime per hour. Later, a manager stopped after one task and scheduled its own wake-up because the brief told it to; the owner corrected it to run tasks back to back. An hourly trigger was eventually turned off at the owner’s request. (`data/main-full.txt` [10-27 01:18, 13:02–15:06; 10-28 00:34–00:36, 18:09–18:24]; `out/w1-chunk-4.md`, `out/w1-chunk-6.md`, `out/w1-chunk-8.md`) **Impact:** repeated interruptions and avoidable idle time; at 16:06 the orchestrator estimated only about 30 minutes of actual runtime since 13:00.

### What worked

- The dispatcher turned sandbox limitations into a narrow file protocol. The manager could request worktree creation and landing, then receive result files; it eventually landed GATE-1 independently [10-27 01:44–02:15; `MANAGER-CODEX.md`].
- Restart recovery preserved work in branches and worktrees, and snapshots gave the owner transferable bundles and run records [10-27 00:01; 10-28 00:16–00:23].
- Classifier denials were surfaced, not silently bypassed. After owner-directed permission changes, the CI push path succeeded; failures that remained—queued Actions jobs—were reported separately [10-28 15:50–16:02].
- Cross-tool handoff succeeded after the Codex usage cap: export/import was tested, the destination was made private, and the Claude manager resumed from the saved state [10-28 00:00–00:23].

### What failed / friction

- The request-file dispatcher, heartbeat protocol, recovery script, keepalive, snapshots, secret scanner and scheduler lifecycle were all hand-built around environment gaps. The git log shows `dispatcher.sh` evolving from worker dispatch into request handlers, while `keepalive.sh` and `recover.sh` were added alongside it (`data/plan-repo-gitlog.txt` [10-26 23:38 onward]; `/home/user/repo/astrid-install/tools/`).
- Several distinct controls were confused in practice: repo privacy did not satisfy the code-exfiltration classifier for CI pushes; a push could succeed while Actions stayed queued; and a settings-file write was blocked as self-modification even after broad owner permission was expressed [10-28 00:16–00:23, 15:50–16:02].
- Liveness signals produced false losses and missing exit markers. Snapshot freshness also depended on a manager remembering to export after landings [10-27 01:26, 04:59–05:35; 10-28 05:58, 16:02].
- Session scheduling and keepalive had separate lifecycles. Reclaim could kill the process meant to keep the container alive; an hourly check did not itself keep work moving, and an incorrect manager brief caused self-scheduled idle periods [10-27 13:02–15:06; 10-28 00:34–00:36].
- The records document lost bookkeeping and stale snapshots, but not a confirmed product patch lost through folder deletion. Treat that example as unverified from the supplied raw sources.

### Candidate principles

- When a manager cannot perform a host operation from its sandbox, expose that operation as a typed, auditable request with a result and failure state, because nested Codex workers could not run shell commands [10-26 23:32–23:38].
- When a worker starts, let one runtime own its heartbeat, exit status, retry and recovery, because workers were falsely marked lost and exit markers disappeared on dispatcher restart [10-27 01:26, 04:59–05:35].
- When a session needs credentials, provision them through a scoped secret store and define which sessions inherit them, because Codex login and API-key visibility differed between local and remote sessions [10-26 01:15; 10-28 10:31–10:44].
- When an external action is denied, return the specific policy reason and a supported owner-approval path, because broad permission statements did not clear classifier refusals [10-28 15:50–15:53].
- When a program runs across sessions or tools, commit/export state at each task boundary and mark its revision and timestamp, because snapshots lagged behind landed work [10-28 05:58, 16:02].
- When work is meant to run continuously, make session lifetime, worker lifetime and scheduled-trigger lifetime one managed policy, because container reclaim and absent triggers repeatedly interrupted execution [10-27 13:02–15:06].
- When context approaches a budget threshold, summarize structured state and rotate at task or phase boundaries, because 263K–281K manager context coincided with concern over repeated-read cost [10-28 01:57–03:57].

### Structure implications

A platform or process should natively provide:

- **Run and worker entities:** model, tool/vendor, task ID, worktree, start time, heartbeat, exit code, final artifact, retry count, cost, and recoverable state.
- **Typed operations:** worktree, dispatch, sync, land, status update and CI submission as permissioned APIs with validated inputs and explicit completion results; avoid maintaining filesystem request conventions in scripts.
- **Durable workspace snapshots:** automatic checkpoint after each landing, branch and run-artifact manifest, export timestamp, secret scan status, and stale-snapshot alert.
- **Credential bindings:** per-provider auth state, scoped secret references, which sessions can read them, and whether a restart is required after rotation.
- **Policy outcomes:** denial category, affected action/data/repository, owner-approval route, and an auditable approval record; clearly distinguish policy permission from provider/API availability.
- **Lifecycle controls:** a single run-level keepalive/reclaim policy, durable scheduled triggers, restart recovery, and an owner-visible pause/stop state.
- **Context and cost fields:** current context size, budget threshold, compaction summary, session lineage, usage limit and planned rotation point.
- **CI run records:** pushed commit tuple, target repository/branch, workflow run ID, queue state, result and timeout; a successful push must not imply successful CI.
- **Handoff checklist:** confirm repo visibility and policy, auth availability, latest snapshot revision, pending workers, uncommitted work, scheduled checks, and any environment-specific model limitations before transferring managers.
