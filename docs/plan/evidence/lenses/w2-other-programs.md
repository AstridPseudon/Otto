## Lens: Other programs and earlier process attempts

### Findings

1. **Observed — The role split recurs; the mechanics change.** The installer program’s operating model made the manager own the queue, worker reviews, landings, and status, while the orchestrator checked progress and unblocked it [10-27 02:52, `out/w1-chunk-4.md`]. The proof-run playbook and timeline handoff describe the same owner → orchestrator → manager → workers chain (`data/other-branches-process-docs.txt:115–136`, `:617–638`, `:1090–1124`). In the current run, the owner again emphasized that the manager should do the work and the orchestrator should shepherd it [10-27 02:52, `data/main-full.txt:4010`; 10-28 16:55, `out/w1-chunk-8.md`]. **Inference:** role separation is a stable primitive; which session or model fills each role is adaptable.

2. **Observed — Durable written state recurs because sessions and workers do not reliably persist.** The process guides treat plans, status, briefs, queue records, and evidence as project memory, with explicit export/import and recovery procedures (`data/other-branches-process-docs.txt:645–669`; `:1237–1263`). The current program similarly required a cold-start review of whether a fresh manager could execute from its documents; that review found missing “Done when” criteria and naming conflicts, which were then corrected [10-26 19:59–20:10, `out/w1-chunk-2.md`]. A later Codex-to-Claude handoff was explicitly requested and carried out [10-28 00:06–00:23, `data/main-full.txt:5573–5938`]. The plan-repo log confirms subsequent handoff and rebase snapshots, including `f12f43a` (“Rebase plan approved with rulings; fresh manager session”) and `956ea36` (rebase complete) [`data/plan-repo-gitlog.txt:2502, :2682`].

3. **Observed — Manager transitions and handoff formats are project-specific.** The proof-run guide exports git bundles, state files, and queue briefs, tests a destination session, then cuts over; it says not to move transcripts or regenerable environments (`data/other-branches-process-docs.txt:645–714`). The timeline program explicitly adapted that process, but combined three Codex leads into one Claude manager after quota exhaustion; it restored multiple repos, test lanes, lead status, and recent evidence (`data/other-branches-process-docs.txt:1090–1124, :1380–1415`). The current UPD program also adapted the handoff guide, with a snapshot repo and product work delivered in a zip [10-28 00:06–00:23, `data/main-full.txt:5573–5938`]. **Inference:** preserve a common handoff contract, but let each project define its payload and delivery boundary.

4. **Observed — Gates and independent review recur, but review cadence differs.** The current program added Astra reviews, review-generated fix tasks, and bounded rounds [10-26 01:37–01:42, `out/w1-chunk-1.md`]. The proof-run guide instead has the manager check every result against acceptance criteria, with Opus reserved for exceptions or a costly gate (`data/other-branches-process-docs.txt:638–643, :175–202`). The timeline manager likewise runs tests and compares acceptance criteria per task, with Opus reserved for failed Sonnet tasks or the final delivery review (`data/other-branches-process-docs.txt:1090–1124`). **Inference:** acceptance checks are stable; how much independent review to add should depend on the stage and risk.

5. **Observed — Frequent oversight was tried repeatedly, with different operating costs.** The current run tried hourly check-ins and a six-hour deep review, then struggled with container sleep and worker restarts [10-26 22:32–22:36, `out/w1-chunk-3.md`; 10-27 14:56–16:06, `out/w1-chunk-4.md`]. The proof-run playbook formalized hourly checks and added 15-minute light checks only during active iteration; it also says scheduled prompts must stay true and blocked managers should not burn no-op turns (`data/other-branches-process-docs.txt:159–175, :748–771`). The owner later turned off the current rebase hourly trigger [10-28 18:09–18:24, `data/main-full.txt:8938–8944`]. **Inference:** cadence needs an explicit lifecycle and a fit to session/runtime behavior, not just a cron interval.

6. **Observed — One-manager-per-program was not universal.** The proof-run design uses two Codex managers for independent tracks, with a foundation gate before the second track forks (`data/other-branches-process-docs.txt:115–137`). The timeline follow-up design used three parallel leads, then staged H → D → P with a fresh manager for each stage (`data/other-branches-process-docs.txt:2178–2210`). The current program mostly used a single manager queue; two Codex managers were planned for the later TST/REL phase after the rebase [10-28 10:48–10:51, `out/w1-chunk-7.md`; `data/plan-repo-gitlog.txt:2531–2544`]. **Inference:** topology should follow independent work and shared-file constraints, not a fixed hierarchy size.

7. **Observed — These programs differed in product-work boundaries.** The current owner specified product work as local branches and a final zip, with a private scratch repo for CI [10-26 01:52–02:01, `out/w1-chunk-1.md`]. The timeline runbook also prohibited upstream pushes and required a final zip, but used local collection branches and a specific staging base (`data/other-branches-process-docs.txt:2115–2142`). The proof-run handoff allowed product-code bundles into the handoff repo’s snapshot branch, while still requiring secret scans and environment-only credentials (`data/other-branches-process-docs.txt:645–669`). These are delivery-policy choices, not a single recurring convention.

### What worked

- **Testing whether a new manager could cold-start exposed actionable doc gaps.** The review found missing completion criteria and ID collisions; revisions then clarified read order, owner decisions, and tracker state [10-26 19:59–20:10, `out/w1-chunk-2.md`].
- **A snapshot-based handoff enabled a manager change after quota exhaustion.** The owner requested the documented Claude handoff, and the transcript records the new manager starting from its brief [10-28 00:06–00:23, `data/main-full.txt:5573–5938`].
- **Review findings could change scope.** Astra’s release-process review led to removing the proposed audit swarm while retaining mandatory checks [10-28 16:50–17:11, `out/w1-chunk-8.md`; `data/plan-repo-gitlog.txt:2667`].
- **Stage boundaries supported fresh contexts.** The UPD process repeatedly started fresh managers at phase/review boundaries to reduce accumulated context and cost [10-28 02:52, 04:54, 09:58, `data/main-full.txt:6590–7044`].

### What failed / friction

- **The intended “orchestrator only shepherds” boundary was difficult to maintain.** The current run needed repeated owner corrections about delegating execution; the orchestrator also handled setup, integration problems, and handoff packaging [10-27 02:52, `data/main-full.txt:4010`; 10-27 02:19, `out/w1-chunk-4.md`; 10-28 16:55, `out/w1-chunk-8.md`].
- **A written cadence did not guarantee work would run.** Container sleep interrupted long tasks under hourly-only operation; keeping the session alive needed a separate mechanism [10-27 14:56–16:06, `out/w1-chunk-4.md`].
- **Tool and runtime assumptions broke the planned topology.** Nested workers could not run shell commands until a dispatcher was added [10-26 23:32–23:38, `out/w1-chunk-3.md`]. The proof-run lessons later document similar failures: workers dying with manager turns, disk loss, stale status, and blocked managers burning no-op turns (`data/other-branches-process-docs.txt:252–265`).
- **Handoff artifacts needed maintenance after creation.** The current program sent multiple replacement zips as the manager note and plan scope changed [10-28 16:36–17:11, `out/w1-chunk-8.md`]. **Inference:** a handoff needs an obvious current version and a change summary when recipients already hold earlier packs.

### Candidate principles

1. **When a program has a manager, make its queue and status the execution source of truth, because all three process families assign queue ownership to the manager and require durable status** (`data/other-branches-process-docs.txt:115–136, :617–638`; [10-27 02:52, `out/w1-chunk-4.md`]).
2. **When transferring work to a new session, export code references, current state, active tasks, and evidence, then test the recipient’s cold start, because stale or incomplete handoffs caused ambiguity and rework** (`data/other-branches-process-docs.txt:645–714`; [10-26 19:59–20:10, `out/w1-chunk-2.md`]).
3. **When deciding review depth, match it to task or stage risk and define the acceptance evidence first, because programs used different review patterns while converging on explicit criteria and tests** (`data/other-branches-process-docs.txt:638–643, :1090–1124`; [10-26 01:37–01:42, `out/w1-chunk-1.md`]).
4. **When work is blocked or a session sleeps, represent the state and next action durably, because repeated restarts and no-op turns otherwise lose time** (`data/other-branches-process-docs.txt:159–175, :252–265`; [10-27 14:56–16:06, `out/w1-chunk-4.md`]).
5. **When choosing parallel managers, gate forks on shared foundations and define file ownership, because the proof and timeline processes explicitly used integration gates and shared-file coordination** (`data/other-branches-process-docs.txt:115–137, :2178–2210`).

### Structure implications

- **Program manifest:** role assignments, manager session, repo/base refs, delivery policy, and current stage.
- **Task entity:** stable ID, dependencies, owner, worker tier, acceptance criteria, evidence links, state, and retry/escalation history.
- **Durable status record:** headline state, running work, blockers, next action, last update time, and the exact code/evidence heads it describes.
- **Handoff snapshot:** versioned code refs or bundles, plans, task state, environment requirements, evidence, and an import/cold-start check; omit secrets and regenerable artifacts.
- **Gate record:** decision, acceptance criteria, test/review evidence, reviewer, and any follow-up tasks.
- **Cadence controller:** check frequency, active iteration mode, manager/session health, and a stop/pause trigger that changes when the operating plan changes.
- **Ownership map:** shared files or foundations, permitted writers, fork prerequisites, and integration path when multiple managers run in parallel.
