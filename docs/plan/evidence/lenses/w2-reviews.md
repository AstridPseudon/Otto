### Candidate principles

- When judging whether a plan solves a reported issue, check the current source revision and label un-reproduced claims, because the initial bundle was 127 commits stale and reversed PATH/skills conclusions (`[10-26 01:12–01:14]`).
- When a design has cross-platform or lifecycle seams, ask a second model to inspect those seams independently, because Opus found erased saved preferences and platform reviews found missing restart/cleanup behavior (`[10-26 01:19–01:29]`).
- When reviewing a plan before implementation, ask for blocking findings, minimal corrective changes, evidence, and deferred risks; route only accepted findings into sized fix tasks, because Astra’s gate review produced five contemporaneous blockers and concrete plan amendments (`[10-26 21:42–21:43]`).
- When complexity is disputed, run separate robustness and over-engineering questions, because one should find missing safeguards while the other removes duplicate machinery (`[10-26 22:18–22:24]`).
- When reviewing an already-built multi-repo integration, use up to three fix-and-rereview rounds, then stop and run final qualification, because UPD’s three rounds found fixes while the immediate deep check added little beyond duplicate coverage (`[10-28 02:57–06:58]`).
- When a review yields only cleanup, keep the pass bounded and route implementation to normal workers; reserve Opus for final critique and judgment calls, because the owner corrected Opus implementation assignments and the 12-item elegance pass was executed by workers (`[10-28 01:29–01:40; 06:58]`).
- When tests fail due to ordering, verify the smallest reproducing pair and affected file before rerunning the whole suite, because R7 full-suite attempts cost about 70 minutes each (`[10-28 14:16–14:17]`).
- When a reviewer proposes broad architecture, require each added mechanism to name the failure it prevents; cut duplicate reporting, caching or audit machinery without evidence of distinct coverage, because Astra recommended removing proof-cache and audit layers while retaining exact-SHA gates (`runs/ASTRA-handover-overeng/final.md`).

### Structure implications

- Represent a **review** as a first-class record: stage/task, purpose (`robustness`, `over-engineering`, `coherence`, `elegance`, `cold-start`), reviewer/model, exact input revision, read-only vs edit authority, start/end, cost, findings and status.
- Require finding fields: severity/blocking, evidence and reproduction status, smallest fix, owner decision (`accept`, `reject`, `defer`) with reason, linked fix task, verification result.
- Add **review round** and **stop rule** fields to a stage: maximum rounds, what triggers another round, and whether final qualification follows. The observed practices vary: three rounds plus elegance for UPD; one review plus qualification for TST.
- Record model policy on the program/task and enforce it at dispatch: Opus review-only; worker tier and model; no routine review after each task unless risk requires it. The owner corrected role drift repeatedly (`[10-28 00:37–01:40]`).
- Add a source-freshness gate: capture commit IDs for every repository, require reviewers to cite them, and invalidate a review when inputs move materially.
- Add review questions in the brief: “What concrete failure does each mechanism prevent?”, “What is the smallest safe design?”, “What remains unproven?”, and “What can be deferred without weakening the stated safety floor?”
