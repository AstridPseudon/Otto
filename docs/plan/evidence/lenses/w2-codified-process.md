## Lens: The process as written vs as practised

### Findings

1. **The written model changed faster than its documentation set.** The original model put git, plans, status, stage gates and taste passes with the orchestrator; the manager coordinated workers and never committed ([README.md](/home/user/repo/astrid-install/README.md), [CODEX.md](/home/user/repo/astrid-install/CODEX.md)). It then shifted to a manager-run queue, first via Codex, then to a Claude Haiku session for UPD when Codex hit its usage limit; the orchestrator’s role narrowed to hourly guidance and checks ([plan-repo-gitlog.txt](/tmp/claude-0/-home-user/61c0e870-3601-52f0-903b-3607ce5e0548/scratchpad/retro/data/plan-repo-gitlog.txt), commits 6d60963, e25dadc; [BRIEF-claude-manager.md](/home/user/repo/handoff-upd/BRIEF-claude-manager.md)). By contrast, README still describes the earlier Codex setup and says scratch CI is unused. The later [MANAGER-CODEX.md](/home/user/repo/astrid-install/MANAGER-CODEX.md) defines TST and REL managers, but those projects were not launched here: the owner said, “you just need to update the zip file” [10-28 16:55], then took over the next phase [10-28 17:00].

2. **“Keep work moving” became an explicit operating rule after the first setup stalled.** The initial nested Codex worker path failed: all four wave-one tasks had escalated before reading or changing files, and this was noticed at 23:32 [10-26 22:57; 10-26 23:32]. The workaround was an external dispatcher [10-26 23:33–23:38]. Later, the owner found the UPD manager had stopped after one task to schedule its own wake-up: “it should just be running through all the tasks back to back” [10-28 00:35]. The brief was corrected to require back-to-back execution, and that rule appears in both later manager briefs.

3. **The manager’s autonomy increased; review cadence decreased.** Early instructions called for Astra review of each X-hard task and more Opus involvement. On 28 Oct the owner corrected Opus’s use twice—first “review work and high-level taste-based work” [10-28 01:29], then “only … five reviews … at the very end” [10-28 01:39]. The resulting Claude-manager brief says no review after each task; the manager checks its own work and asks for a reviewer only when it cannot judge. It still uses bounded end-of-project review rounds and an elegance pass ([BRIEF-claude-manager.md](/home/user/repo/handoff-upd/BRIEF-claude-manager.md), “How each task goes” and “Final phase”). **Observed:** the owner kept the final review gate and narrowed routine review. **Inference:** review was retained where it could assess system-level completeness, while per-task review was treated as cost and latency.

4. **Recovery rules were added in response to real process failures.** Container restarts killed manager, dispatcher and workers [10-26 23:58]; the runbook then gained restart recovery, heartbeats, `worker.exit`/`lost` handling, resume-from-worktree instructions and snapshot procedures (git log commits 01d2576, 0702d4e, 9709254, d4a9605). Disk limits and long-running tests also became explicit: the final rebase recorded **1,021 agent tests not run (hung)** [10-28 20:56], after the manager had been told to run bounded chunks and record hung tests [10-28 16:58]. **Inference:** durable, inspectable run state was necessary because the process could not rely on a continuously alive session or a complete suite finishing promptly.

5. **The evidence rules held up better than the staffing and tool choices.** The docs repeatedly require tests and their outputs, real-caller checks, and “written, not run” for unavailable Windows, macOS or CI proof ([MANAGER.md](/home/user/repo/astrid-install/MANAGER.md), “Review” and “Rules”; [MANAGER-CODEX.md](/home/user/repo/astrid-install/MANAGER-CODEX.md), “Principles”). In practice, the owner explicitly required new-failure-only comparisons [10-28 01:52]; the rebase used `origin/main` as its baseline [10-28 13:04, 15:28], and the orchestrator told the manager to fix a new failure but not chase a failure already on the shipping base [10-28 20:21]. At closeout, incomplete tests were labeled unrun rather than passed [10-28 20:56].

6. **The release-skill draft was a detailed procedure for work that did not occur in this run.** It defines normal, hotfix, App-only, Runtime-hop, Pinokio and recovery paths, with human stop points before pushes or Railway actions ([astrid-deploy-SKILL.md](/home/user/repo/astrid-install/plans/drafts/astrid-deploy-SKILL.md)). `PROGRAM.md` says the release-safety and installer program was paused in favor of UPD, and the draft calls itself an interim checklist until the deploy gate exists. **Observed:** the transcripts show no deployment using this skill. **Inference:** its rules were not tested by this program’s execution; they remain candidate process documentation, not demonstrated practice.

7. **The stable core was about ownership and evidence, not a fixed toolchain.** The git history records major changes to dispatcher, worker count, model tiers, manager type, review cadence and delivery route (e.g. commits e635b21, a52509f, e25dadc, 4d840c4, 92d9b84). Across these revisions, a project still had a named task list, scoped work, a manager responsible for execution, and an evidence-based completion decision. The exact implementation—Codex versus Claude, dispatcher versus direct sub-agents, per-task versus end-stage review—was not stable.

### What worked

- **A task queue gave the manager an execution spine.** UPD formally closed its main queue, then produced a rebase plan for orchestrator approval before execution [10-28 09:54–09:59]. The queue and completion markers made phase boundaries visible ([BRIEF-claude-manager.md](/home/user/repo/handoff-upd/BRIEF-claude-manager.md), “The task list” and “Then the rebase”).
- **The orchestrator could steer without taking over implementation.** It approved the rebase plan with two concrete rulings—“merge instead of replaying” and “no repinning”—then handed execution to a fresh manager session [10-28 09:58–09:59].
- **Explicit comparison baselines prevented unnecessary fixes.** The owner’s new-failures-only rule became part of the test process; final evidence distinguished regressions and test-setup issues [10-28 01:52; 10-28 20:21–20:39].
- **The handover had a clear end condition.** REBASE-COMPLETE was checked, the final package was built and sent, and the manager was archived [10-28 20:38–20:56].

### What failed / friction

- **The initial execution mechanism was not validated end to end.** The first wave appeared assigned but had produced no work by the time it was inspected [10-26 22:57; 23:32]. Later heartbeats and failure states made work more observable, but only after the failure.
- **Instructions caused idleness before they were corrected.** The owner had to diagnose the manager’s scheduled self-wake behavior [10-28 00:34–00:36]. “Back-to-back” was important enough to recur in later briefs.
- **Model rules were easy to misapply.** Opus was assigned implementation/design work before the owner repeatedly narrowed it to final reviews and elegance [10-28 01:29–01:40]. The model table changed again when the owner requested Luna/Terra/Sol for a later Codex phase [10-28 10:31–10:33]; that phase was ultimately not run here.
- **The file set contains stale and conflicting instructions.** README says scratch CI is “Not used”; later `MANAGER-CODEX.md` has an Actions workflow, and the owner authorized CI pushes at 11:00 [ORCHESTRATOR.md, “Next phase”; 10-28 11:00]. `GOAL.md` is explicitly superseded, while CODEX.md retains stage-based mechanics alongside newer manager briefs. **Inference:** readers must know which file and phase takes precedence, a burden that can recreate outdated behavior.
- **The final verification had a material gap.** The final pack was sent with hung tests recorded, not run [10-28 20:38–20:56]. That is honest evidence handling, but it means queue completion was not equivalent to full test completion.

### Candidate principles

- **When a project starts, name one authoritative queue and integration branch; make each run link to both, because the queue drove UPD completion and rebase while plan status and handoff files also existed.** ([BRIEF-claude-manager.md](/home/user/repo/handoff-upd/BRIEF-claude-manager.md), “The task list”; [10-28 09:54–09:59])
- **When a worker or manager is idle and startable work remains, dispatch eligible work immediately and expose the idle reason, because scheduled self-wakes caused avoidable stoppage.** ([MANAGER-CODEX.md](/home/user/repo/astrid-install/MANAGER-CODEX.md), “Principles”; [10-28 00:34–00:36])
- **When a task’s acceptance is unclear, approve a scoped Done when and its proving test before implementation, because early task setup encountered unapproved criteria and unclear task boundaries.** ([MANAGER.md](/home/user/repo/astrid-install/MANAGER.md), “Done when”; [plan-repo-gitlog.txt](/tmp/claude-0/-home-user/61c0e870-3601-52f0-903b-3607ce5e0548/scratchpad/retro/data/plan-repo-gitlog.txt), commits 0d87b94 and b8ef3d5)
- **When declaring tests complete, compare against the project’s chosen base and label unavailable or hung checks “not run,” because only new failures were actionable and the final run left tests unfinished.** ([BRIEF-claude-manager.md](/home/user/repo/handoff-upd/BRIEF-claude-manager.md), “Final test run”; [10-28 20:21–20:56])
- **When handing work to a new manager or owner, version the handover and state which instructions supersede older ones, because several active documents describe different phases and permissions.** ([README.md](/home/user/repo/astrid-install/README.md); [ORCHESTRATOR.md](/home/user/repo/astrid-install/ORCHESTRATOR.md), “Superseded” and “Next phase”; [10-28 16:55–17:11])

### Structure implications

- **Program/project entity:** owner, orchestrator, manager, worker model, integration branch, queue path, allowed repos/actions, lifecycle status and current phase.
- **Task/run entity:** scope, dependencies, tier/model, Done when, brief, attempts, worker state/heartbeat, test output, “written/not run” evidence, resulting commits and review findings.
- **Decision/ruling record:** timestamp, source (owner/orchestrator), affected tasks, superseded rule and whether it applies immediately. Render the currently effective policy into every brief.
- **Handover record:** source and target manager, snapshot revision/time, queue and branch pointers, remaining work, open blockers, test gaps, permissions and trigger lifecycle. Mark old docs as historical or link them to the current operating guide.
- **Automatic cadence/trigger:** dispatch ready rows when capacity frees; alert on stale worker heartbeat or snapshot; pause scheduled checks when ownership changes or completion is recorded.
- **Completion checklist:** queue empty, expected end marker present, landed commits recorded, baseline comparison complete, every unrun check named, and handover package tied to the exact branch heads.
