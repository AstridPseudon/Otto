## 1. Findings

**High — `otto save` can read the wrong file at CUTOVER.** [The `otto` client](/private/tmp/otto-audit-tree/src/otto/portfolio/cli.py:1689) makes `--directory` absolute but forwards a relative save filename unchanged at [line 1759](/private/tmp/otto-audit-tree/src/otto/portfolio/cli.py:1759). The owner then [opens that filename](/private/tmp/otto-audit-tree/src/otto/portfolio/cli.py:1215) in its own process. If the operator runs `otto --portfolio P save project.json` from a project folder while the owner has another working directory, the save fails—or reads a different `project.json` there. Deleting the old Store after a mistaken save could lose the intended project data. The `ottoctl portfolio save` path [already makes the filename absolute](/private/tmp/otto-audit-tree/src/otto/hostctl/portfolio.py:115).

Proposed fix row **SAVE-CWD** — Resolve the save file against the caller’s working directory before forwarding it. Files: `src/otto/portfolio/cli.py`, client tests. Acceptance: with distinct caller and owner directories containing different `project.json` files, `otto save project.json` saves the caller’s file; this fails before the fix. **Route: normal.**

**High — Repointing a host lane leaves other Otto client locators on the old owner.** Host admission writes [a `client.json` lane pointer](/private/tmp/otto-audit-tree/src/otto/hostctl/service.py:507). Separately, `otto` sends to the owner lane selected by [`--home`/`OTTO_HOME`/`~/.otto`](/private/tmp/otto-audit-tree/src/otto/portfolio/cli.py:1753), and the maintained [orchestrator setup instructions](/private/tmp/otto-audit-tree/src/otto/portfolio/skills/orchestrator-setup/SKILL.md:8) and [orchestrator client default](/private/tmp/otto-audit-tree/src/otto/portfolio/orchestrator_client.py:325) select `~/.otto/orchestrator-connection.json`. **Inference:** if a Codex or r4 session keeps that connection or an old `OTTO_HOME`, admitting its host to the new owner does not move that session. After the old owner stops, its requests fail or continue addressing an old lane. I found no new-locator writer in `src/otto/hostctl`.

Proposed fix row **CLIENT-CUTOVER** — Inventory and repoint host homes, `otto` service-home selection, connection locators, and issued bindings at the turn boundary; read back owner identity and project scope from each client before stopping the old owner. Files: `src/otto/hostctl/{config,service}.py`, `src/otto/portfolio/{cli,orchestrator_client}.py`, maintained Otto skills, cutover tooling. Acceptance: a client using each supported locator reaches the new owner after the old owner stops, and an old binding is refused. **Route: xhard.** A plausible local mistake is copying an old binding to the new locator, crossing the owner identity and project-scope boundary.

**Medium — `otto show project` reports success for an incomplete task page.** The command exposes [`--limit` but no cursor](/private/tmp/otto-audit-tree/src/otto/portfolio/cli.py:93). It calls the paged reader once and returns [`outcome: read` with only that page](/private/tmp/otto-audit-tree/src/otto/portfolio/show.py:32); the underlying reader reports [`has_more` and a cursor](/private/tmp/otto-audit-tree/src/otto/portfolio/intake.py:1042). For a 101-task project, the default read shows 100 tasks and still says `read`. A CUTOVER diff that treats that outcome as a complete read can miss an unsaved task before deletion.

Proposed fix row **SHOW-COMPLETE** — Drain all pages for `show project`, or expose a cursor and mark nonterminal pages explicitly incomplete. Files: `src/otto/portfolio/{show,cli}.py`. Acceptance: a 101-task project cannot yield a complete-looking 100-task response; this fails before the fix. **Route: normal.**

**Medium — A fresh install has no configured managed product restart.** [`ottoctl install`](/private/tmp/otto-audit-tree/src/otto/hostctl/cli.py:216) records a [new installation without `owner_composition`](/private/tmp/otto-audit-tree/src/otto/hostctl/config.py:85). Foreground [`service run` works without it](/private/tmp/otto-audit-tree/src/otto/hostctl/cli.py:845), but [`product_argv` refuses it](/private/tmp/otto-audit-tree/src/otto/hostctl/supervision.py:290), and `launchd_definition` requires that composition. If the new owner exits after the old one stops, this fresh installation has no generated managed restart path. COMPOSE queues the product launchd form; the fresh-install configuration that selects it remains a separate gap.

Proposed fix row **INSTALL-RESTART** — Configure and verify product composition for a fresh install before the CUTOVER switch. Files: `src/otto/hostctl/{cli,config,supervision}.py`. Acceptance: a fresh `install --create` yields a valid product launch definition that restarts `service run` against that installation’s home and source; this fails before the fix. **Route: xhard.** A plausible mistake is restarting through a different source edition than the one staging qualified.

## 2. Checked and sound

- `ottoctl install`, `ottoctl service run`, and `otto save` entry points exist; the foreground product start is selected for a fresh installation. [CLI](/private/tmp/otto-audit-tree/src/otto/hostctl/cli.py:49), [service selection](/private/tmp/otto-audit-tree/src/otto/hostctl/cli.py:845).
- Save requires an existing project’s base revision and refuses stale writes; its response carries a diff. [Save parser](/private/tmp/otto-audit-tree/src/otto/portfolio/save.py:37), [owner apply](/private/tmp/otto-audit-tree/src/otto/portfolio/herzchen_binding.py:2389).
- `ottoctl project status` enumerates the project’s tasks and document hashes. [Status read](/private/tmp/otto-audit-tree/src/otto/hostctl/cli.py:518). Its task dependency field is only a count, so it alone is insufficient for an exact task diff.

[Tasklist](${TRANSFER_ROOT}/portfolio/projects/program/tasklist.md:67), [CUTOVER](${TRANSFER_ROOT}/portfolio/projects/program/tasklist.md:151).
