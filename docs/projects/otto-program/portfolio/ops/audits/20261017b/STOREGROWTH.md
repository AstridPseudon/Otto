## 1. Findings

**Store accounting.** A committed `mutate` adds one `events` row and one `command_receipts` row, updates or creates one current `identities` row, advances one `event_sequences` row and the append counter, and inserts any new reference rows. A `work.*` revision also retains a full payload snapshot in `record_references`. The configured history projection normally adds at least one `project_history` row. Replaying the same request key adds nothing. Evidence: [store.py:2309](/private/tmp/otto-audit-tree/src/herzchen/kernel/store.py:2309), [store.py:2363](/private/tmp/otto-audit-tree/src/herzchen/kernel/store.py:2363), [store.py:2080](/private/tmp/otto-audit-tree/src/herzchen/kernel/store.py:2080), [history.py:183](/private/tmp/otto-audit-tree/src/herzchen/kernel/history.py:183).

**Illustrative day, explicitly an inference:** Four continuously busy workers completing one task each per hour, with each task then completed by its manager, produce **96 tasks and at least 1,056 events and 1,056 receipts per day** from the eleven identified mutations per task. Result observations, assessment, retries, other gateway writes and saves add to that count. At 16 KiB of ASCII instructions per worker, the guide revision, current Due head and four Due events retain at least **9 MiB/day of repeated instruction text alone**. There is no fixed total byte estimate: ordinary Work and Due payloads have no general Store byte cap, and SQLite indexes and page overhead add space. [execution.py:453](/private/tmp/otto-audit-tree/src/otto/portfolio/execution.py:453), [attention.py:431](/private/tmp/otto-audit-tree/src/otto/attention.py:431), [attention.py:1437](/private/tmp/otto-audit-tree/src/otto/attention.py:1437).

**A. Assessment coverage eventually refuses unrelated new work.** Evidence: [assessment.py:120](/private/tmp/otto-audit-tree/src/otto/portfolio/assessment.py:120) reads the entire shared `assessment` stream and refuses when it contains more than 10,000 events; [manager_assessment_command.py:74](/private/tmp/otto-audit-tree/src/otto/portfolio/manager_assessment_command.py:74) requires that coverage to find a task’s required scope. Scenario: 10,001 assessment events across old projects, then a manager checks a new task with one scope → coverage raises before examining that task. At the illustrative rate of three assessment events per completed task, the threshold arrives in about 35 days. Real use: an unrelated history total can stop reviews and landing setup. **Proposed row, normal:** use the existing parent-scoped event predicate in `src/otto/portfolio/assessment.py` and keep the completeness bound on that parent’s results. Acceptance: more than 10,000 unrelated assessment events leave one task’s coverage and required scope usable; an oversized *same-parent* history still refuses explicitly. The predicate already exists in [store.py:2727](/private/tmp/otto-audit-tree/src/herzchen/kernel/store.py:2727).

**B. Each worker instruction is retained repeatedly in Due history.** Evidence: preparation stores `instructions` in a guide and again in Due ([execution.py:449](/private/tmp/otto-audit-tree/src/otto/portfolio/execution.py:449), [execution.py:501](/private/tmp/otto-audit-tree/src/otto/portfolio/execution.py:501)); every Due save copies the whole record into event effects ([attention.py:1437](/private/tmp/otto-audit-tree/src/otto/attention.py:1437)); native-body factoring excludes `instruction` ([retained_native.py:323](/private/tmp/otto-audit-tree/src/otto/agents/retained_native.py:323)). Scenario: a 16 KiB instruction and ordinary prepare, start and finalize → four retained event copies, a current Due copy and a guide copy, before runtime writes. Real use: disk growth follows repeated state changes even though instruction text is immutable. **Proposed row, xhard:** make Due history carry an exact guide revision ref and digest; resolve those exact bytes only at the provider/replay boundary. Files: `src/otto/portfolio/execution.py`, `src/otto/attention.py`, `src/otto/agents/retained_native.py` and its reader. Acceptance: four Due revisions do not each add instruction-sized event bytes, while a restart and replay deliver byte-identical instructions. **Plausible cross-component mistake:** resolving the current guide head instead of the pinned revision changes a replayed worker’s instructions.

**C. Status scans retained identities from every project.** Evidence: portfolio status requests tasks, assignments, Due records and reports by project ([status.py:151](/private/tmp/otto-audit-tree/src/otto/portfolio/status.py:151)); its generic reader selects each kind with a parameterized `json_extract(payload_json, ?)`, returns all matches and has no limit ([store.py:1562](/private/tmp/otto-audit-tree/src/herzchen/kernel/store.py:1562), [store.py:1587](/private/tmp/otto-audit-tree/src/herzchen/kernel/store.py:1587), [store.py:1602](/private/tmp/otto-audit-tree/src/herzchen/kernel/store.py:1602)). The optional Due project expression index cannot serve that parameterized expression as written. Scenario: after roughly 35,000 one-hour worker records in a year under the illustrative rate, asking status for one small project evaluates retained Due rows belonging to the others. Real use: polling cost rises with owner lifetime rather than the selected project. **Proposed row, normal:** route the known project selectors through literal, declared expression indexes, including the existing Due project index; add equivalent declared selectors for the other status kinds. Keep the full selected-project result. Acceptance: query plans for status with 10,000 foreign records use indexed project lookups and return the same selected-project rows. Files: `src/herzchen/kernel/schema.py`, `src/herzchen/kernel/store.py`, `src/otto/portfolio/status.py`.

**D. Narrow history questions materialize the whole event ledger.** Evidence: unfiltered `list_events()` does `SELECT e.* ... fetchall()` with no cursor or limit ([store.py:2680](/private/tmp/otto-audit-tree/src/herzchen/kernel/store.py:2680), [store.py:2754](/private/tmp/otto-audit-tree/src/herzchen/kernel/store.py:2754)). Task-ID discovery, document backlinks, attention and even a cursor-based responsibility view call it unfiltered ([timeline.py:80](/private/tmp/otto-audit-tree/src/herzchen/domains/work/timeline.py:80), [packets.py:457](/private/tmp/otto-audit-tree/src/herzchen/content/packets.py:457), [packets.py:636](/private/tmp/otto-audit-tree/src/herzchen/content/packets.py:636), [packets.py:650](/private/tmp/otto-audit-tree/src/herzchen/content/packets.py:650)). Scenario: one backlink or attention read after months of four-worker operation loads every unrelated event body. Real use: latency and memory grow without a per-request bound. **Proposed row, xhard:** add indexed, cursor-paged event selectors for these exact questions and migrate these callers; require an explicit finite page size. Acceptance: with 30,000 unrelated events, each question reads bounded pages and returns the same links, attention and cursor delta. **Plausible cross-component mistake:** selecting only current heads loses historical links or changes visibility decisions. Files: `src/herzchen/kernel/store.py`, `src/herzchen/content/packets.py`, `src/herzchen/domains/work/timeline.py`.

**E. Every successful history rebuild leaves the old projection generation behind.** Evidence: rebuild deletes rows only for the *new* generation before filling it, then switches `history_generation` without deleting previous generations ([project_history.py:422](/private/tmp/otto-audit-tree/src/herzchen/kernel/project_history.py:422), [project_history.py:453](/private/tmp/otto-audit-tree/src/herzchen/kernel/project_history.py:453)). Scenario: rebuild the same Store three times → three full projected histories occupy `project_history`; only the newest is active. Real use: a repair operation multiplies history storage and its five index sets. **Proposed row, normal:** after verified generation switch, delete retired generations in bounded batches; let SQLite reuse pages and document offline `VACUUM` for shrinking the file. Acceptance: three rebuilds leave one generation’s rows, and a cursor from a prior generation still requests refresh. File: `src/herzchen/kernel/project_history.py`.

The five growth tables are `identities` (new record IDs), `record_references` (new pins and full Work revision snapshots), `command_receipts`, `events` and `project_history`; `event_sequences` also grows with distinct streams. Source events, receipts and Work snapshots have no ordinary compaction. The queued **RET** row already owns general Store retention, so I am not proposing that row again. Its design must preserve request replay and historical revision pins, and account for the gapless event check in [store.py:1209](/private/tmp/otto-audit-tree/src/herzchen/kernel/store.py:1209). `CleanClose` does strip selected native transcript fields for finished projects; it keeps rows, and file shrinkage requires offline `VACUUM`. [clean_close.py:1](/private/tmp/otto-audit-tree/src/otto/agents/clean_close.py:1), [clean_close.py:25](/private/tmp/otto-audit-tree/src/otto/agents/clean_close.py:25).
