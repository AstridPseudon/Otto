## 1. Findings

**The ten findings are ordered by severity.** “Exposure rank” estimates how often an agent would encounter the path from source reachability and routine use; Otto telemetry was not available, so these ranks are inferences. The proposed rows concern refusal UX and do not repeat the underlying defects in STAGE2 or the queued tasklist rows.

1. **Manager recovery is offered by the domain but cannot be submitted through `ottoctl manager`** (exposure rank 10). [manager_client.py:52](/private/tmp/otto-audit-tree/src/otto/hostctl/manager_client.py:52) parses only `report_key`, `operation`, and `new_report_key`; [manager_continuation_command.py:218](/private/tmp/otto-audit-tree/src/otto/portfolio/manager_continuation_command.py:218) requires nine exact pins and a request key for `dispose-no-overlap`. The preprovider disposition similarly requires pins and a disposition ([manager_preprovider_disposition.py:127](/private/tmp/otto-audit-tree/src/otto/portfolio/manager_preprovider_disposition.py:127)). An unknown manager effect → `dispatch` returns “current manager unknown effect requires owner disposition” with no `next_action` ([manager_continuation_command.py:123](/private/tmp/otto-audit-tree/src/otto/portfolio/manager_continuation_command.py:123)); the advertised CLI cannot supply the required recovery input. This can strand a project after an uncertain turn. **Rewrite:** “Held: this manager turn has an unknown effect. Read `manager-continue --operation status --report-key KEY`; have the owner verify the returned no-overlap evidence, then submit `dispose-no-overlap` with those exact pins and a fresh request key. Do not replay the unknown turn.” **Fix row:** expose a typed disposition input in `hostctl/manager_client.py`, return that action from `manager_continuation_command.py`, and cover the preprovider counterpart. Acceptance: a CLI-level status → exact disposition → continuation check succeeds; missing or changed pins fail before the fix and after it. **Route: xhard.** A plausible mistake is accepting a disposition without exact pins, permitting a second provider effect.

2. **A completed owner write can be reported as an unexplained error** (exposure rank 1 for the shared wrapper). [service.py:486](/private/tmp/otto-audit-tree/src/otto/hostctl/service.py:486) applies admission, then its `finally` appends a log at [service.py:492](/private/tmp/otto-audit-tree/src/otto/hostctl/service.py:492). If that append fails, the common handler returns only `outcome:error`, exception type/message, and `provider_called:false` ([service.py:339](/private/tmp/otto-audit-tree/src/otto/hostctl/service.py:339)). The agent cannot tell whether admission persisted or what to inspect before repeating it. **Rewrite:** “The admission reply failed after owner processing; admission state is uncertain. Read the task’s current admission and this retained request receipt before retrying the same request key. Do not submit a new admission intent.” **Fix row:** add effect-aware error and `next_action` handling in `hostctl/service.py`, preserving the request token. Acceptance: inject a log-append failure after successful admission; the reply reports uncertainty and a readback action, while the task remains admitted. **Route: xhard.** A plausible mistake is treating `provider_called:false` as proof that no owner write occurred.

3. **`ottoctl` exits successfully for held and pending commands** (exposure rank 4). [hostctl/cli.py:1123](/private/tmp/otto-audit-tree/src/otto/hostctl/cli.py:1123) returns zero for every outcome except five named failure values; a lane timeout returns `pending`, `terminal:false`, effects unknown ([lanes.py:121](/private/tmp/otto-audit-tree/src/otto/hostctl/lanes.py:121)). A shell agent can therefore advance its workflow while Otto says the command has not completed. The `otto` CLI assigns nonzero to these outcomes ([portfolio/cli.py:1633](/private/tmp/otto-audit-tree/src/otto/portfolio/cli.py:1633)). **Rewrite:** keep the pending JSON and its existing `next_action`, but state “Request ID is pending; completion is unconfirmed,” and exit nonzero. **Fix row:** align outcome-to-exit handling in both CLI files. Acceptance: `pending`, `held`, and `unknown` produce nonzero exit codes; terminal success produces zero. **Route: normal.**

4. **A worker’s failed `done` check is labeled `owner_unavailable`** (exposure rank 6). [landing.py:119](/private/tmp/otto-audit-tree/src/herzchen/fleet/landing.py:119) raises “admitted check failed; lab returned to worker”; [facade.py:218](/private/tmp/otto-audit-tree/src/herzchen/fleet/tools/facade.py:218) converts this ordinary landing refusal into `error:owner_unavailable`, with no `next_action`. A worker may pursue owner recovery when it needs to fix its retained lab. **Rewrite:** “Landing refused: the admitted check failed on the rebased lab. Fix the check failure in this retained lab, run `check`, then submit `done` again.” **Fix row:** give landing failures stable, stage-specific codes and actions in `fleet/landing.py` and `tools/facade.py`. Acceptance: failed admitted check returns `check_failed`, identifies the retained lab, and gives that action; it currently returns `owner_unavailable`. **Route: xhard.** A plausible mistake is giving retry advice to a failure that occurred after line advancement.

5. **A second `run-worker` request is held without naming its recovery command** (exposure rank 5). [manager_journey_service.py:2314](/private/tmp/otto-audit-tree/src/otto/portfolio/manager_journey_service.py:2314) finds a prior worker that is unstarted, active, or uncertain and returns `held` with its schedule ID, but no `next_action` ([manager_journey_service.py:2320](/private/tmp/otto-audit-tree/src/otto/portfolio/manager_journey_service.py:2320)). The manager knows there is a prior occurrence but is left to guess whether to retry or create another key. **Rewrite:** “Held: task TASK already has worker occurrence SCHEDULE with unconfirmed settlement. Run `ottoctl manager worker-status --task TASK --principal PRINCIPAL --schedule-id SCHEDULE`; reconcile that occurrence before requesting another worker.” **Fix row:** add this action to the held result in `manager_journey_service.py`. Acceptance: the prior-worker case names the exact status command and creates no second occurrence. **Route: normal.**

6. **A failing `check` looks like a successful tool call** (exposure rank 3). [landing.py:59](/private/tmp/otto-audit-tree/src/herzchen/fleet/landing.py:59) returns feedback with `result.ok:false` and a nonzero exit code; [facade.py:198](/private/tmp/otto-audit-tree/src/herzchen/fleet/tools/facade.py:198) wraps it in top-level `ok:true`, `feedback:true`, `accepted:false`, without an action. The outer MCP reply therefore is not marked as an error ([stdio_server.py:66](/private/tmp/otto-audit-tree/src/herzchen/fleet/tools/stdio_server.py:66)). The transport did succeed, but the nested result is easy to miss. **Rewrite:** “Check ran and failed (exit N); this is feedback, not acceptance. Inspect the admitted check output, fix the lab, and call `check` again.” **Fix row:** add explicit `check_passed:false` and `next_action` to the check response in `tools/facade.py`, retaining transport `ok:true`. Acceptance: a nonzero check exit yields those fields and remains unaccepted. **Route: normal.**

7. **Portfolio input errors claim `read_only:true` even for mutation requests** (exposure rank 2). [portfolio/cli.py:1347](/private/tmp/otto-audit-tree/src/otto/portfolio/cli.py:1347) routes broad validation failures through [portfolio/cli.py:487](/private/tmp/otto-audit-tree/src/otto/portfolio/cli.py:487), which always sets `read_only:true` and omits `next_action`. For example, malformed `complete-task` input is a failed mutation request ([portfolio/cli.py:660](/private/tmp/otto-audit-tree/src/otto/portfolio/cli.py:660)); its reply gives a field error but misleading operation metadata. **Rewrite:** “Completion request was rejected before the owner call: FIELD is missing or invalid. Correct FIELD; inspect current task state before resubmitting a mutation.” **Fix row:** make the error builder operation-aware in `portfolio/cli.py`, with pre-effect status and a specific corrective action. Acceptance: malformed completion input reports a mutation request with `effects_started:false` and the named correction; read commands remain marked read-only. **Route: normal.**

8. **Native `ask` and `wait` failures lack a usable action** (exposure rank 7). Without the authenticated caller socket, `otto ask` says only that the socket is required ([portfolio/cli.py:1717](/private/tmp/otto-audit-tree/src/otto/portfolio/cli.py:1717)). A valid `otto wait` that times out returns a cursor but no `next_action` ([manager_journey_service.py:1888](/private/tmp/otto-audit-tree/src/otto/portfolio/manager_journey_service.py:1888)); `timeout` also exits zero under [portfolio/cli.py:1633](/private/tmp/otto-audit-tree/src/otto/portfolio/cli.py:1633). An asker may move on without an answer or try again from an unauthenticated shell. **Rewrite:** socket case: “Run `otto ask` inside the owner-launched assignment that has its caller socket.” Timeout case: “No answer yet; repeat this exact wait with the original issue/session scope and returned cursor.” **Fix row:** add those actions and a nonterminal timeout exit to `portfolio/cli.py` and `manager_journey_service.py`. Acceptance: both responses contain the stated action; timeout is nonzero. **Route: normal.**

9. **Presence rejection does not distinguish what the operator should do next** (exposure rank 9). [service.py:473](/private/tmp/otto-audit-tree/src/otto/hostctl/service.py:473) distinguishes declined, timeout, and unavailable proof states, but [service.py:481](/private/tmp/otto-audit-tree/src/otto/hostctl/service.py:481) gives all of them “local operator presence was not proved” and no `next_action`. An orchestrator can only guess whether to wait for the operator, repeat a timed-out proof, or repair the prover. **Rewrite:** declined: “The operator declined this admission; stop and await a new operator decision.” Timeout: “Presence timed out; ask the operator to retry this exact admission.” Unavailable: “Presence service is unavailable; restore it before retrying.” **Fix row:** status-specific guidance in `hostctl/service.py`. Acceptance: each injected proof state yields its distinct action and no admission write. **Route: normal.**

10. **Worker tool discovery and validation hide the remedy** (exposure rank 8). The facade returns `unauthorized`, `forbidden`, or `bad_args` with `detail` but no `next_action` ([facade.py:157](/private/tmp/otto-audit-tree/src/herzchen/fleet/tools/facade.py:157), [facade.py:169](/private/tmp/otto-audit-tree/src/herzchen/fleet/tools/facade.py:169)); MCP `tools/list` converts an invalid-token refusal into an empty tool list ([stdio_server.py:52](/private/tmp/otto-audit-tree/src/herzchen/fleet/tools/stdio_server.py:52)). A worker with an expired grant sees no tools and no explanation; an undeclared argument likewise gives no valid call shape. **Rewrite:** invalid grant: “This assignment’s tool grant is no longer valid; return to the owner for a current assignment. Do not reuse the token.” Bad arguments: name the tool’s allowed arguments (`check`: none; `done`: `summary`). **Fix row:** preserve a safe discovery error and add schema-specific actions in `tools/stdio_server.py` and `tools/facade.py`, without exposing tokens. Acceptance: invalid-token listing is distinguishable from a valid empty list, and a bad `done` argument names the allowed shape. **Route: normal.**
