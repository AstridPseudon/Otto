## Findings

### 1. Claude initializer processes are absent from durable owner custody

**Evidence:** [claude_adapter.py:423](/private/tmp/otto-audit-tree/src/otto/agents/claude_adapter.py:423) starts an initializer before the work turn. [claude_cli.py:372](/private/tmp/otto-audit-tree/src/otto/agents/claude_cli.py:372) starts it in a separate process group, but [claude_cli.py:377](/private/tmp/otto-audit-tree/src/otto/agents/claude_cli.py:377) calls the owner’s process pin only for non-initializers. Owner restart cleanup reads recorded groups ([execution_host.py:1083](/private/tmp/otto-audit-tree/src/otto/portfolio/execution_host.py:1083)).

**Scenario → outcome:** A forced owner stop during a held Claude initializer leaves its group running without a `capacity-process-groups.json` entry. The queued ORPHANWORKER cleanup cannot identify it. **Inference:** the initializer can outlive its owner, as the work process did in STAGE2.

**Fix row — INITCUSTODY, xhard:** Pin initializer groups before they run and retain every group belonging to an occurrence until each is proven gone. Files: `claude_cli.py`, `claude_adapter.py`, `execution_host.py`. Acceptance: hold an initializer, force-stop the owner, and prove the group is gone; repeat with an initializer that leaves a child before the work group starts. A plausible single-group replacement would lose the initializer’s child when the work group is pinned.

### 2. A failed durable process pin is silently accepted

**Evidence:** [execution_host.py:725](/private/tmp/otto-audit-tree/src/otto/portfolio/execution_host.py:725) records a process and [execution_host.py:729](/private/tmp/otto-audit-tree/src/otto/portfolio/execution_host.py:729) writes the durable file. Both layers of [owner_runtime.py:53](/private/tmp/otto-audit-tree/src/otto/agents/owner_runtime.py:53)–[67](/private/tmp/otto-audit-tree/src/otto/agents/owner_runtime.py:67) swallow write and owner errors. Claude calls that hook after process creation but before input ([claude_cli.py:372](/private/tmp/otto-audit-tree/src/otto/agents/claude_cli.py:372)–[381](/private/tmp/otto-audit-tree/src/otto/agents/claude_cli.py:381)).

**Scenario → outcome:** Make the process-group file unwritable. A Claude work process starts, its pin fails, and the prompt still proceeds. After an owner crash, restart cleanup has no durable identity to kill or reconcile. This is a sibling of ORPHANWORKER: that row handles groups *that were recorded*.

**Fix row — PINFAIL, xhard:** Treat pin persistence as required launch admission; terminate the newly born group before useful input if it fails, and retain an unknown attempt. Files: `owner_runtime.py`, `claude_cli.py`, `src/herzchen/adapters/host.py`. Acceptance: inject a pin-write failure for each provider and prove no useful input, no surviving group, and an inspectable failed/unknown attempt. A plausible mistake is returning a prelaunch failure while the already created process remains alive and eligible for retry.

### 3. Direct runtime entry can bypass host capacity and process custody

**Evidence:** Without a current bounded host, [execution.py:1211](/private/tmp/otto-audit-tree/src/otto/portfolio/execution.py:1211)–[1228](/private/tmp/otto-audit-tree/src/otto/portfolio/execution.py:1228) calls `_gated_start` directly. It still checks worker readiness and records dispatch ([execution.py:1309](/private/tmp/otto-audit-tree/src/otto/portfolio/execution.py:1309)–[1347](/private/tmp/otto-audit-tree/src/otto/portfolio/execution.py:1347)), but the capacity reservation is in the host queue ([execution_host.py:914](/private/tmp/otto-audit-tree/src/otto/portfolio/execution_host.py:914)–[923](/private/tmp/otto-audit-tree/src/otto/portfolio/execution_host.py:923)). Without host context, adapter transport executes directly ([execution_host.py:975](/private/tmp/otto-audit-tree/src/otto/portfolio/execution_host.py:975)–[977](/private/tmp/otto-audit-tree/src/otto/portfolio/execution_host.py:977)) and the process pin records nothing ([owner_runtime.py:53](/private/tmp/otto-audit-tree/src/otto/agents/owner_runtime.py:53)–[58](/private/tmp/otto-audit-tree/src/otto/agents/owner_runtime.py:58)). Lifecycle delivery also calls `invoke_role` directly ([lifecycle.py:548](/private/tmp/otto-audit-tree/src/otto/portfolio/lifecycle.py:548)).

**Scenario → outcome:** **Inference, because I found no current service caller using the fallback:** a caller holding an `ExecutionApplication` invokes `assign_and_start` outside the bounded owner. A ready worker can start with a dispatch and native sandbox, but without a charged host slot or durable process-group fence.

**Fix row — BOUNDEDSTART, xhard:** Require bounded owner context at the final provider boundary and route any supported direct/lifecycle delivery through that owner. Files: `execution.py`, `owner_runtime.py`, `lifecycle.py`. Acceptance: an otherwise valid direct call starts no provider and consumes no attempt; the same request through the owner charges capacity first. A plausible fix at `ExecutionApplication.start` alone leaves `LifecycleIntegration → invoke_role` open.

### 4. Ordinary manager turns have no assignment dispatch event

**Evidence:** Initial manager activation calls `app.start` ([serve.py:636](/private/tmp/otto-audit-tree/src/otto/hostctl/serve.py:636)–[654](/private/tmp/otto-audit-tree/src/otto/hostctl/serve.py:654)); ordinary `continue_manager` also reaches `start` ([execution.py:2216](/private/tmp/otto-audit-tree/src/otto/portfolio/execution.py:2216)–[2223](/private/tmp/otto-audit-tree/src/otto/portfolio/execution.py:2223)). The shared start records `WorkAssignments.dispatch` only when `due.role == "worker"` ([execution.py:1340](/private/tmp/otto-audit-tree/src/otto/portfolio/execution.py:1340)–[1347](/private/tmp/otto-audit-tree/src/otto/portfolio/execution.py:1347)). Answer-session continuation has a separate dispatch call ([execution.py:2042](/private/tmp/otto-audit-tree/src/otto/portfolio/execution.py:2042)–[2048](/private/tmp/otto-audit-tree/src/otto/portfolio/execution.py:2048)).

**Scenario → outcome:** A current manager starts or resumes normally; its Due attempt and capacity exist, but no `work.assignment.dispatched` event names that turn. Auditors cannot reconcile every provider turn to one dispatch using the Work domain. MANUALDISPATCH covers the five worker paths, not these manager turns.

**Fix row — ROLEDISPATCH, normal:** Record one idempotent dispatch per non-worker occurrence before its provider call, using a key specific to that occurrence; preserve the answer continuation’s existing receipt. Files: `execution.py`, `src/herzchen/domains/work/assignments.py` if role semantics need adjustment. Acceptance: initial manager, ordinary continuation, and replay produce respectively one, one, and zero new dispatch events; worker behavior remains one per start.
