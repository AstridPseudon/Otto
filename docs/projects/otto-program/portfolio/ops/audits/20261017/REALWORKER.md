## Findings

1. **The worker’s MCP helper can be selected from the lab checkout.**  
   Evidence: [product_service.py:809](/private/tmp/otto-audit-tree/src/otto/hostctl/product_service.py:809) launches the configured Python with `-m herzchen.fleet.tools.stdio_server`; [claude_cli.py:372](/private/tmp/otto-audit-tree/src/otto/agents/claude_cli.py:372) runs Claude in the lab directory; [claude.py:110](/private/tmp/otto-audit-tree/src/herzchen/fleet/hosts/claude.py:110) allows network by default; [pins.py:42](/private/tmp/otto-audit-tree/src/herzchen/fleet/tools/pins.py:42) records executable paths without hashing the MCP Python or its module. **Inference:** if a checkout contains a top-level `herzchen` package, Python’s `-m` lookup can load its `stdio_server` instead of Otto’s. That process receives the worker token and has network access. A real worker could see forged `task`, `check`, or `done` replies, and the token could leave the machine.  
   **Proposed fix row — xhard:** run the MCP helper from verified, isolated code; pin and recheck its interpreter and module bytes at launch. Files: `product_service.py`, `claude_cli.py`, `pins.py`, Claude host launch. Acceptance: a lab containing a shadow `herzchen` package cannot replace the server, and changing either helper binary or module after pinning refuses launch. Plausible mistake: pinning Python alone while `-m` still imports checkout code.

2. **A legitimate Edit-only worker can land, then settle `unknown`.**  
   Evidence: [claude.py:25](/private/tmp/otto-audit-tree/src/herzchen/fleet/hosts/claude.py:25) grants both `Edit` and `Write`; [claude_adapter.py:66](/private/tmp/otto-audit-tree/src/otto/agents/claude_adapter.py:66) captures only successful `Write` calls and [claude_adapter.py:106](/private/tmp/otto-audit-tree/src/otto/agents/claude_adapter.py:106) rejects a result with none. Landing has already advanced the line when post-turn capture runs ([landing.py:211](/private/tmp/otto-audit-tree/src/herzchen/fleet/landing.py:211), [claude_adapter.py:463](/private/tmp/otto-audit-tree/src/otto/agents/claude_adapter.py:463)); capture errors become `unknown`, without replay ([claude_adapter.py:488](/private/tmp/otto-audit-tree/src/otto/agents/claude_adapter.py:488)). A Haiku worker that edits existing source and test files using `Edit`, calls `check` and `done`, can therefore merge valid work while its owner result remains uncaptured and its lab cannot be swept. The same mismatch occurs after a `Write` followed by an `Edit` to that file. This is separate from the queued LABCAPTURE ordering fix.  
   **Proposed fix row — xhard:** capture and verify the final changed artifacts for both editing tools before settling a landed result. Files: `claude_adapter.py`, owner capture/cleanup predicate, tests. Acceptance: Edit-only and Write-then-Edit native streams land, capture their final committed bytes, settle completed, and remove the lab; an altered file still fails. Plausible mistake: accepting a git diff as native delivery evidence without tying its files and bytes to the authorized turn.

3. **A refused landing has no product route to resume its worker.**  
   Evidence: [landing.py:106](/private/tmp/otto-audit-tree/src/herzchen/fleet/landing.py:106) aborts a conflicting rebase and retains the lab. Herzchen defines exact-session continuation ([contract.py:369](/private/tmp/otto-audit-tree/src/herzchen/fleet/hosts/contract.py:369)), but the Claude adapter explicitly rejects `resume` for a worker ([claude_adapter.py:371](/private/tmp/otto-audit-tree/src/otto/agents/claude_adapter.py:371), [claude_adapter.py:389](/private/tmp/otto-audit-tree/src/otto/agents/claude_adapter.py:389)); source callers of `run_continuation` are tests only. Once a conflict response ends a bounded native turn, the owner cannot deliver its landing log to that same worker session. The stage 4 harness compounds this by deleting the refused lab immediately ([perch.sh:563](/private/tmp/otto-audit-tree/ops/bootstrap/perch.sh:563), [perch.sh:578](/private/tmp/otto-audit-tree/ops/bootstrap/perch.sh:578)) and requiring that deletion in its report ([perch_report.py:1520](/private/tmp/otto-audit-tree/ops/bootstrap/perch_report.py:1520)).  
   **Proposed fix row — xhard:** retain the refused lab and exact attempt; authorize a bounded continuation of the same worker session with the conflict log; delete the lab only after the eventual captured landing or an explicit settled abandonment. Files: `claude_adapter.py`, owner execution/recovery, `perch.sh`, `perch_report.py`. Acceptance: force a conflict after a passing worker check, observe unchanged canon and retained lab, resume the same session, resolve it, then observe one verified landing and lab removal. Plausible mistake: launching a fresh session or deleting the lab while an uncertain prior effect remains.

4. **The real-model stage gates are absent.**  
   Evidence: [perch.sh:807](/private/tmp/otto-audit-tree/ops/bootstrap/perch.sh:807) rejects nonfake stages above 2; [project.json:5](/private/tmp/otto-audit-tree/ops/bootstrap/canary/project.json:5) declares stages 0, 1, 2 and 4, with no stage 3. Stage 4’s `--fake` path runs `fake_worker.py` and a shell merge ([perch.sh:524](/private/tmp/otto-audit-tree/ops/bootstrap/perch.sh:524)); its owner-driven assertion is skipped in fake mode ([perch_report.py:1506](/private/tmp/otto-audit-tree/ops/bootstrap/perch_report.py:1506)). Thus `perch.sh 3` cannot start, `perch.sh 4` cannot use Haiku, and a passing fake report proves no real model journey.  
   **Proposed fix row — xhard:** add the three-task real stage 3 and owner-driven real stage 4, sourcing assertions from owner Due, runner, landing and capture records. Files: canary `project.json`, `perch.sh`, `perch_report.py`, focused perch tests. Acceptance: nonfake stages 3 and 4 run and each assertion turns red when its owner evidence is removed. Plausible mistake: synthesizing owner events from harness bookkeeping, yielding a pass without product execution.

5. **A Codex worker cannot use this owner-managed path today.**  
   Evidence: a Codex host entry declares a Codex adapter ([config.py:118](/private/tmp/otto-audit-tree/src/otto/hostctl/config.py:118)), but `HostOwnerService` defaults every execution to `_claude_adapter` ([serve.py:118](/private/tmp/otto-audit-tree/src/otto/hostctl/serve.py:118)); that factory calls `compose_claude`, which requires Claude settings and a qualified Claude model ([adapters.py:45](/private/tmp/otto-audit-tree/src/otto/hostctl/adapters.py:45)). Register a Codex host and dispatch its normal Codex model: composition fails before its worker runs. The generic Codex host has MCP rendering ([codex.py:127](/private/tmp/otto-audit-tree/src/herzchen/fleet/hosts/codex.py:127)), but it is not selected here.  
   **Proposed fix row — xhard:** select the owner adapter by the admitted host kind and qualify Codex’s lab, MCP grant, sandbox and result capture on the same journey. Files: `serve.py`, `adapters.py`, Codex binding, owner journey tests. Acceptance: a Codex worker calls `task`, `check` and `done` through the owner, lands on the sealed commit and leaves no lab. Plausible mistake: switching adapters while dropping the token-bound MCP grant or workspace fence.
