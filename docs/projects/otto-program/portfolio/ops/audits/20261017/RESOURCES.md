## Findings

Rate convention: with four continuously occupied worker slots and mean turn duration **τ seconds**, turnover is **R = 14,400/τ launches per hour** (240/hour if τ is one minute). Status, document, and check rates depend on callers; four occupied slots alone do not fix those rates. Counts below are source estimates, not measurements.

1. **Owner-routed requests rebuild a socket-bearing bootstrap.** Evidence: the resident owner routes operations through `HOST_OPERATIONS` ([service.py:441](/private/tmp/otto-audit-tree/src/otto/hostctl/service.py:441)); each routed `HostSession` constructs `PortfolioOwnerBootstrap` ([owner.py:221](/private/tmp/otto-audit-tree/src/otto/hostctl/owner.py:221)), which constructs at least eight command facades ([owner_bootstrap.py:681](/private/tmp/otto-audit-tree/src/otto/portfolio/owner_bootstrap.py:681), [owner_bootstrap.py:702](/private/tmp/otto-audit-tree/src/otto/portfolio/owner_bootstrap.py:702), [owner_bootstrap.py:748](/private/tmp/otto-audit-tree/src/otto/portfolio/owner_bootstrap.py:748)). It activates the create/open bridge ([owner_bootstrap.py:781](/private/tmp/otto-audit-tree/src/otto/portfolio/owner_bootstrap.py:781)). Facades register socket services ([command_ports.py:630](/private/tmp/otto-audit-tree/src/herzchen/command_ports.py:630)); `HostSession.__exit__` closes only an owned Store ([owner.py:243](/private/tmp/otto-audit-tree/src/otto/hostctl/owner.py:243)). **Scenario:** repeatedly request project or portfolio status on the running owner → the response succeeds, while service sockets, temp directories, and an activated bridge thread remain until process exit. **Rate:** at *H* routed requests/hour, at least **8H socket services/temp directories and H bridge threads/hour**, plus nested services; *H* is not determined by four workers. This can exhaust descriptors or threads during ordinary observation. **Fix row — xhard:** reuse correctly scoped owner capabilities or close the complete transient facade graph after each call. Files: `hostctl/owner.py`, `portfolio/owner_bootstrap.py`, `herzchen/command_ports.py`. Acceptance: 200 owner-routed status/admit calls leave socket, thread, and temp-directory counts flat while identities remain distinct. Plausible mistake: sharing a cached bootstrap across host principals borrows another principal’s authority. This identifies a remaining construction path beyond the named LIMITFD `role_runtime` site.

2. **Resident project views construct more facades on reads and assessment.** Evidence: every manager status with an assessment policy constructs `LimitService` ([manager_journey_service.py:656](/private/tmp/otto-audit-tree/src/otto/portfolio/manager_journey_service.py:656)); project-document reads construct `ContextPacketService` ([serve.py:423](/private/tmp/otto-audit-tree/src/otto/hostctl/serve.py:423)); `manager_assessment()` constructs `AssessmentModule` ([owner_bootstrap.py:1072](/private/tmp/otto-audit-tree/src/otto/portfolio/owner_bootstrap.py:1072)), whose engine exposes a reader, limits, and operations ([module.py:258](/private/tmp/otto-audit-tree/src/herzchen/domains/assessment/module.py:258)). The facade constructor starts services for those exposed companions ([command_ports.py:633](/private/tmp/otto-audit-tree/src/herzchen/command_ports.py:633)). Reviewed activation also constructs a fresh `LimitService` when `_pool` is reached ([reviewed_activation.py:306](/private/tmp/otto-audit-tree/src/otto/portfolio/reviewed_activation.py:306)). **Scenario:** manager status, document reads, assessment preparation, or activation on an otherwise stable owner → sockets and temp directories accumulate with no call-site close. **Rate:** approximately **2S + 2D + 4A + 2P services/hour**, for *S* status, *D* document, *A* assessment, and *P* reached pool calls. If each of four workers induces *s* status requests/hour, status alone adds **8s services/hour**. These sockets bind immediately; serving threads start only if a transport is activated. **Fix row — normal:** retain these facades at their owner or project scope, or close every service created for a transient call. Files: the four call sites above and `command_ports.py`. Acceptance: repeated calls through each path keep descriptor and temp-directory counts flat; assessment and document authorization still use the caller’s scope.

3. **Runner result evidence grows indefinitely and each new run scans it all.** Evidence: the product retains `ResultStore` under `home/runner-results` ([product_service.py:1233](/private/tmp/otto-audit-tree/src/otto/hostctl/product_service.py:1233)); each submitted run gets a sealed JSON record ([runner.py:104](/private/tmp/otto-audit-tree/src/herzchen/fleet/runner/runner.py:104)) and an output log ([runner.py:292](/private/tmp/otto-audit-tree/src/herzchen/fleet/runner/runner.py:292)). `next_seq()` reads and sorts **all** records on every new run ([store.py:124](/private/tmp/otto-audit-tree/src/herzchen/fleet/runner/store.py:124), [store.py:142](/private/tmp/otto-audit-tree/src/herzchen/fleet/runner/store.py:142)); no result-record or log removal path was found. **Scenario:** four workers each run *c* checks per turn → **cR JSON records and cR logs/hour**, with variable log bytes; later submissions repeatedly load the growing history. Owner restart releases no files. This is separate from the queued kernel Store-retention task, RET. **Fix row — xhard:** retain replay and evidence identity in a compact index and define bounded archival/reclamation for terminal run bodies. Files: `fleet/runner/store.py`, `fleet/runner/runner.py`, product composition. Acceptance: after many terminal runs, new-run admission does bounded work and retained bytes follow the declared policy while old run IDs still produce an unambiguous evidence/replay answer. Plausible mistake: deleting a terminal record lets its ID be reused or removes the proof behind an accepted check.

4. **Ambiguous shared-host responses can accumulate, and pruning has a fixed throughput ceiling.** Evidence: `home/shared-host` is the product’s `ExecutionHost` directory ([product_service.py:1250](/private/tmp/otto-audit-tree/src/otto/hostctl/product_service.py:1250)); responses are pruned at most once per minute, 200 at a time ([execution_host.py:1471](/private/tmp/otto-audit-tree/src/otto/portfolio/execution_host.py:1471)). The retention policy excludes `unknown`, pending, oversized responses without a terminal projection, and responses with live markers ([ipc_retention.py:29](/private/tmp/otto-audit-tree/src/otto/portfolio/ipc_retention.py:29), [ipc_retention.py:99](/private/tmp/otto-audit-tree/src/otto/portfolio/ipc_retention.py:99)). Each scan holds and sorts every response entry ([ipc_retention.py:100](/private/tmp/otto-audit-tree/src/otto/portfolio/ipc_retention.py:100)). **Scenario:** distinct worker requests settle `unknown` without later reconciliation → at **U such requests/hour, at least U response files/hour** persist and every prune scan grows. Even terminal traffic above **12,000 responses/hour** outpaces the batch limit by the excess. Successful traffic below that rate is released after the 24-hour grace. **Fix row — xhard:** move ambiguous-response recovery identity to a compact durable receipt and bound body retention; make terminal pruning drain a backlog. Files: `portfolio/ipc_retention.py`, `portfolio/execution_host.py`, response readers. Acceptance: old unknown handles remain safely reconcilable after their bulky responses are reclaimed, and a terminal backlog above 200/minute eventually shrinks. Plausible mistake: treating `unknown` as safe to replay after deleting its only receipt.

5. **Worker history rewrites and rescans every prior attempt for an alias.** Evidence: replacing a worker schedule appends the entire previous launch snapshot to `state["worker_history"][task]` ([manager_journey_service.py:2447](/private/tmp/otto-audit-tree/src/otto/portfolio/manager_journey_service.py:2447)); `_save_state` writes the whole state file ([serve.py:174](/private/tmp/otto-audit-tree/src/otto/hostctl/serve.py:174)), which is reloaded after restart ([serve.py:141](/private/tmp/otto-audit-tree/src/otto/hostctl/serve.py:141)). Execution setup scans every historical schedule to reject a stale worker Due ([manager_journey_service.py:187](/private/tmp/otto-audit-tree/src/otto/portfolio/manager_journey_service.py:187)). **Scenario:** repeatedly retry or reroute the same four task aliases with new schedules → **one full snapshot per replacement** remains on disk and in memory; at one replacement per turn, **R snapshots/hour**. State writes and later execution setup grow with history. **Fix row — xhard:** retain compact schedule tombstones or an indexed durable lookup while bounding full snapshots. Files: `manager_journey_service.py`, `serve.py`. Acceptance: hundreds of replacements keep state size and execution setup time bounded, and an old schedule still cannot obtain the current worker lab. Plausible mistake: trimming IDs removes the stale-Due fence.

6. **Dispatch and lab-pair maps retain settled generations.** Evidence: every fresh dispatch inserts a `DispatchRecord` ([dispatch.py:107](/private/tmp/otto-audit-tree/src/herzchen/fleet/dispatch.py:107)); `finish()` revokes the token but leaves the record ([dispatch.py:225](/private/tmp/otto-audit-tree/src/herzchen/fleet/dispatch.py:225)). The owner registry aliases that map and adds Due-key/binding entries ([product_service.py:441](/private/tmp/otto-audit-tree/src/otto/hostctl/product_service.py:441), [product_service.py:871](/private/tmp/otto-audit-tree/src/otto/hostctl/product_service.py:871)). Its `(repo, branch)` lab/landing pair cache also only inserts ([product_service.py:636](/private/tmp/otto-audit-tree/src/otto/hostctl/product_service.py:636)); `close()` stops the tool server but does not evict these maps ([product_service.py:459](/private/tmp/otto-audit-tree/src/otto/hostctl/product_service.py:459)). **Scenario:** continuous new assignments → **R retained records/hour**, and Due bridging can add **2R mapping entries/hour**. Changing branch on each launch adds up to **R cached pairs/hour**; stable branches add none. Memory is released at owner process exit, not settlement. **Fix row — xhard:** evict settled objects only after retaining the minimum generation/replay fence; evict branch pairs only when no lab or landing uses them. Files: `fleet/dispatch.py`, `hostctl/product_service.py`. Acceptance: many distinct settled assignments and branches leave resident map sizes bounded, while duplicate dispatch and stale Due attempts are still refused. Plausible mistake: deleting a settled record makes its assignment ID look fresh.

With four configured running aliases it makes roughly **288,000 current-task reads and 288,000 Due reads/hour** ([product_service.py:925](/private/tmp/otto-audit-tree/src/otto/hostctl/product_service.py:925)); the steady path constructs no socket, thread, subprocess, or Store event.
