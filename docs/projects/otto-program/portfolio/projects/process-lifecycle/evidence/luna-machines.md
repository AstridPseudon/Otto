**Verdict: keep the `Container` idea as the shared lifecycle contract, but narrow the backend promise.** For Mac and Linux now, a retained leader in a fresh POSIX session/process group is the smallest useful backend. Treat cgroups, external container runtimes, and Windows Job Objects as separate capabilities to add when those environments are actually supported.

- **macOS:** `start_new_session=True` gives the leader a new session and process group; ordinary Chrome helpers launched as child processes generally inherit that group. Chromium’s macOS code uses normal child-process launching, but its docs also describe service processes launched through `launchd`. So don’t assume every browser-related process stays in the group: check the actual headless-shell process tree on this Mac. The proposal’s inherited environment tag can help find escaped helpers; `--user-data-dir` is a useful locator for diagnostics, but not proof of process ownership. Chromium’s [process-launch code](https://chromium.googlesource.com/chromium/src/base/%2B/master/process/launch_mac.cc) and [service-process notes](https://chromium.googlesource.com/website.git/%2B/HEAD/site/developers/design-documents/service-processes/index.md) support that distinction.

- **Linux:** use the same session/group backend whether or not cgroup v2 or systemd user services are available. `systemd-run --user --scope` is optional: a user manager may be absent, and containers often run without systemd. A cgroup backend is stronger where Astrid can create and control the cgroup; `cgroup.kill` kills processes in that cgroup tree ([kernel docs](https://kernel.org/doc/html/v5.19/admin-guide/cgroup-v2.html)). Don’t make its availability a prerequisite.

- **RunPod and Docker:** “the runtime is the container” works only when Astrid owns the container lifecycle. Astrid running *inside* a supplied container may have no rights to create or stop sibling containers. In that case, use the POSIX group backend inside the container; PID 1 signal handling and reaping belong to the container entrypoint/runtime and need explicit deployment checks.

- **Windows:** Job Objects with kill-on-close are the right future backend, but require a native Windows implementation. POSIX sessions, `killpg`, and Unix sockets are not portable substitutes. Don’t claim Windows support until that backend exists.

Keep the abstraction at spawn, observe, stop, close, and report. Make capability discovery explicit, rather than promising identical enforcement across all platforms. **Minimum viable backends: one POSIX session/group backend for macOS and Linux; add a Windows Job Object backend before Windows support.** Add cgroups only where deployment access is confirmed; don’t build a generic container-runtime backend yet.

One caveat: the proposal’s “re-check identity immediately before each signal” does not fully guarantee G2 for tag-based PID sweeps. On macOS, a process can exit and its PID be reused between the check and `kill(pid)`. Retaining the leader protects its group ID from reuse, but not arbitrary tagged PIDs. Keep the guarantee scoped to retained group members unless a backend can signal an incarnation-bound handle.
