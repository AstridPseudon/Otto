**Verdict: “one container per execution” fits short task attempts, but it does not fit all Astrid lifetimes.** The smallest useful shared abstraction is an **owner-bound lifetime scope**: an owner holds the identity and cleanup handle for either a task attempt or a leased service. The scope may contain several processes and control relationships; its backend can vary by platform or remote target.

- **Remotion render CLI, ffmpeg, Python pack actions:** These fit task scopes. The generic host launches each admitted capability in an owned process group and monitors it through completion ([`generic_host.py:7841–7853`](astrid/core/execution/generic_host.py:7841), [`process_group.py:253–255`](astrid/core/execution/process_group.py:253)). ffmpeg and other helpers can live inside that attempt’s scope. The Remotion CLI’s separate validation probes are also short owned commands ([`remotion_runtime.py:133–160`](astrid/core/rendering/remotion_runtime.py:133)).

- **Managed Codex image run:** The outer Codex invocation fits a task scope, but the scope must not absorb Codex’s sandbox or command-inventory custody. Those are separate boundaries with their own policies and authority. The abstraction should let the task scope own the process lifetime while preserving those nested controls.

- **Remotion frame owner:** This does **not** fit “one container per execution” if that means one per task attempt. The host session keeps one Node frame worker alive across sequential task leases ([`remotion_host_session.py:75–94`](astrid/core/execution/remotion_host_session.py:75), [`:131–169`](astrid/core/execution/remotion_host_session.py:131)). Treat it as a service scope with task leases. That also gives a clean way to bring a launchctl-submitted owner under an explicit owner rather than pretending it is a task child.

- **VibeComfy native engine graph:** This is a long-lived, multi-role service scope, not one ordinary command. `_NativeEngineGraph` retains an engine and a separately registered listener, with role-bound custody and a control channel ([`generic_host.py:12371–12417`](astrid/core/execution/generic_host.py:12371), [`:12464–12492`](astrid/core/execution/generic_host.py:12464)). Flattening these into a single group kill risks losing the listener’s distinct identity and cleanup protocol. Keep the graph under one service owner, while allowing its members to have role-specific handles.

- **Pack host itself:** It is also a service lifetime. The proposal’s resident host owner is the right direction; represent the host as a scope owned by that resident owner, and task attempts as child scopes.

- **RunPod worker:** This is a remote physical-target lifetime, not a local process container. Its owner is bound to the pod, keeps a target lock, and uses Linux pidfds for exact stop ([`worker_process.py:519–549`](astrid/packs/runpod/worker_process.py:519), [`:412–468`](astrid/packs/runpod/worker_process.py:412)). Keep it behind the same lifecycle contract, but let its backend own a remote process incarnation rather than assuming local group/session membership.

So the generalization should be **one owner-bound scope/handle API, with task scopes and leased service scopes**, not one container per execution. Keep the common contract small—launch or attach, retain identity, stop, report settled or unresolved—and let platform-specific backends provide the mechanism. I would not make environment-tag sweeps a universal guarantee: they do not express the distinct ownership and role boundaries these cases already require.
