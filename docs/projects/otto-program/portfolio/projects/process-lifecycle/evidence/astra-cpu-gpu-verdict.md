**Verdict: approve the shared cleanup-obligation model; revise every row’s categorical CPU/GPU distinction.** Hardware, service lifetime, ownership, billing and containment are independent dimensions. Shared ledger machinery is appropriate; backend enforcement differs substantially.

1. **Cost — directionally right.** Local CPU leaks are consequential on this busy 8 GB Mac. Billing belongs to provider allocations, including CPU allocations. Keep maximum billable lifetime separate from idle retention; short retention must justify repeated model-loading costs. RunPod’s recorded `terminate_at` still does not establish independently enforced shutdown.

Wan2GP’s [persistent implementation explicitly remains a CPU-testable seam pending native qualification](${ORIGINAL_HOME}/Developer/astrid-video/astrid-local/main-20261015/Astrid/astrid/packs/wan2gp/src/persistent.py:5).

3. **Ending one task — conditional.** Protocol cancellation fits a borrowed engine; owned disposable GPU processes can be stopped. Cancellation needs acknowledgement and quiescence before another borrower enters. Engine termination must also allow fault recovery, explicit shutdown and replacement—not only idle/billing policy. Preserve VibeComfy’s control protocol.

4. **Release evidence — overstated on both sides.** A CPU leader’s disappearance does not prove its helpers or external effects ended. Ordinary CUDA allocations normally disappear with their owning process/context; universal device-memory proof is excessive. Surviving workers, shared NVIDIA MPS servers and driver faults require separate treatment; aggregate VRAM usage cannot attribute a leak. [NVIDIA’s explanation](https://forums.developer.nvidia.com/t/does-cpu-process-wait-when-calling-cuda-code/54013/3), [MPS ownership](https://docs.nvidia.com/deploy/mps/appendix-tools-and-interface-reference.html). `_NativeEngineGraph` currently establishes process custody, not CUDA-memory clearance. For pods, authoritative provider termination evidence suffices.

5. **Unresolved blocking — “never the host” is wrong.** Use the **smallest known safe conflict domain**. CPU survivors can retain ports, shared caches or memory; GPU survivors can write shared outputs. Unknown ownership or a driver-wide fault can justify broader quarantine.

6. **Admission — current-state correction is right; proposed allocation is premature.** `vram_bytes` is a minimum-capacity filter. [Reservations are exclusive named keys scoped per executor](${ORIGINAL_HOME}/Developer/astrid-video/astrid-local/main-20261015/Runtime/runtime_protocol/store.py:3428), so two executors sharing a physical GPU need coordinated ownership. GPUs are not intrinsically exclusive. Start with explicit device sets and coarse serialization. Multi-GPU identities must survive visibility remapping; summed VRAM is not necessarily usable model capacity. Defer quantitative packing until measurements require it.

7. **Health — qualify.** CPU memory pressure matters too. GPU OOM does not automatically mean a wedged device. Prefer bounded, backend-specific readiness checks and fault-triggered quarantine; a successful probe cannot guarantee subsequent allocation. Avoid a universal per-task GPU diagnostic.

8. **Location — broadly right, incomplete.** Metal/PyTorch MPS performs GPU work despite ordinary process ownership. Apple Silicon [shares CPU/GPU memory](https://developer.apple.com/documentation/metal/mtldevice/hasunifiedmemory); budget combined pressure without double-counting separate RAM/VRAM pools. These adapters do not establish native MPS qualification. Provider cleanup must distinguish owned versus attached pods, stop versus terminate, and persistent storage: [stopped RunPod storage remains billable](https://docs.runpod.io/pods/manage-pods).

Keep durable acquisition intent, exact release authority, scoped obligations and provider reconciliation. Defer a generic GPU scheduler, mandatory VRAM-clearance proofs and topology machinery.
