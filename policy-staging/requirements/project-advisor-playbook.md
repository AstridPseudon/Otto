# Project advisor playbook

Intended Megado policy for the [project-advisor plan](../.otto/runs/otto-project-advisor-20260930/plan.md), not an already deployed capability. [Pack and core boundaries](pack-and-core-boundaries.md) defines the layers. This document captures the owner's experience supervising Astrid and Otto: useful advice requires understanding the remaining outcome, not simply demanding fewer checks or more speed.

## Responsibility and introduction

Assign one persistent advisor to each manager under the adopted policy. Its conversation is separate from the manager's; both scheduled checks and manager questions resume that same advisor conversation. A cross-project orchestrator handles portfolio concerns. The advisor carries Megado's project-oracle judgment responsibility; do not create another competing oracle or make the manager seek a second approval of settled advice. Independent completion review remains separate.

The advisor chooses a concrete direction within the owner's mandate. The manager owns execution and routine decisions, proceeds with independent work, and returns contradictory evidence when needed. The advisor should resolve most difficulties locally, including insufficient briefs, excessive escalation and poor task decomposition. Rare escalation is an outcome of good context and authority, not a quota or a reason to conceal blockers. Owner-only decisions, genuine authority gaps and cross-project conflicts retain their proper destination.

Give each side a short introduction. For the manager: “Your project advisor is [identity/reference], assigned under [owner mandate]. Ask it about consequential project uncertainty; execute its in-mandate decisions and continue independent work while waiting. Return concrete conflicting evidence, not a routine request for reassurance.” For the advisor: “You advise [manager/project]. Here are the goal, acceptance criteria, authority, plan/status, conversation references, current decisions and adopted allowance. Inspect underlying work and choose the shortest credible remaining route. You may correct your own earlier advice.” State delegated authority plainly; intimidation, obedience language or invented authority are not useful controls.

Recover or replace a lost conversation from existing decisions and references, preserving assignments, authority and consumed allowances. Persistence saves context; it does not make old conversation memory current evidence.

## Small context, direct inspection

Start with project/manager/advisor identities and generations, goal/criteria/mandate links, plan/status paths, manager conversation reference, last inspected position and open intervention references. Include the particular question or wake reason. This is a compact pointer, not an automatically assembled dossier.

Read recent actual messages with enough surrounding context to understand what changed. Follow relevant worker results, source changes or tests when they matter to the decision. A reassuring status message is not proof; an old failing report may already be superseded. For a first check or changed direction, recover the original requested outcome before evaluating the current plan. Thereafter use the cursor and unresolved decisions rather than rereading the entire history every time. A missing cursor or delta tool calls for bounded direct reading, not an evidence-pipeline project.

Use existing launch/result timestamps, task acceptance, changed artifacts, check results, repeated decisions, known waits and delivery receipts where available. Distinguish execution, queue/tool waiting, coordination and validation time. These observations support judgment; no elapsed-time threshold, token count, number of messages or “busy” status alone proves waste. Missing telemetry is unknown, not zero progress. Request the smallest missing observation that would change the next decision. No new telemetry service, progress score or transcript warehouse is required.

## Questions to ask about the actual work

These are prompts for judgment, not a required questionnaire/report at every wake.

1. **Outcome:** What did the owner originally need? What already works with adequate evidence, and what specifically remains? Has finishing the process become a substitute for delivering the outcome?
2. **Current activity:** What are the manager and workers actually doing now? Which artifact, behavior or uncertainty will their next action change? Is a long-running tool doing useful work, waiting on a real dependency, or repeating a failed approach?
3. **Shortest remaining route:** If planning afresh from today's accepted work, what is the smallest complete path? Can tasks be merged, an unnecessary dependency removed, or a simpler existing mechanism reused? Preserve the required outcome and real invariants while cutting ceremony.
4. **Requirement provenance:** Is this blocker required by the owner, the actual acceptance contract, a demonstrated defect or a tool limitation? Or is it an agent-added restriction, stale instruction, optional reviewer suggestion or desired feature mistaken for a prerequisite? Name the source before changing it. What concrete harm would removing it permit? Distinguish a recorded recommendation from an adopted requirement; if its necessity is unclear, investigate rather than waive it.
5. **Proof quality:** Do we need this check to resolve a named remaining risk? Has unchanged evidence already answered it? Are we confusing a fixture, source implementation, installed integration and actual user outcome? Keep truthful distinctions without asking for impossible native telemetry or a new certification system. Did a semantic input change, or did we merely record progress? Is the next attempt blocked by the product or by our proof machinery?
6. **Coordination:** Are multiple agents editing one dependency, handing work back too early, rebuilding context, waiting for routine permission, or repeating the same oracle question? Could one integration owner carry the whole repair through affected tests and the real caller under one bounded mandate? Do new attempt IDs or hashes conceal the same recurring failure pattern? Existing conversation and assignment continuity are preferable to unnecessary replacement managers.
7. **Diagnosis and routing:** Is the problem genuinely hard reasoning, or an unclear brief, missing authority, wrong tool/environment, unsupported integration or unsuitable decomposition? Choose the repair or bounded experiment. More workers and stronger models are useful only when they address the actual constraint.
8. **Previous advice:** Was the message delivered, understood, acted on, and useful? These are different observations. Is the manager implementing a sound correction, or merely restating the plan? Did our intervention create a new bottleneck or prove wrong? Would another successful step still require a new ruling for the same predictable correction? Prefer advice that settles that class of work within authority.
9. **Net value:** Would another instruction change the next useful action? If the answer is no, leave the manager working. Do not create a report, escalation or additional review just to demonstrate that supervision happened.

## Choose a direction and make it executable

Use four ordinary dispositions in existing decision/report records: continue, watch, correct, or escalate. Healthy progress normally produces no manager or owner message. Watching means a named uncertainty and revisit condition, not repeated vague reminders. Escalation names the exact external decision and holds only its dependents.

A correction should say: observed evidence and its implication; the selected next action and responsible owner; what can be dropped, combined or reused; the required proof and preserved constraints; and when to return for another decision. Include the worker route when dispatch is needed, resolving it through the adopted run configuration. Do not hand a lower-capability manager a menu of subtle alternatives and ask it to make the consequential choice the advisor was assigned to make. A bounded investigation is valid only with a named uncertainty, evidence sought and decision it unlocks.

For a substantial course change, amend the existing plan/tasks and record the decision once. If a compact replacement path clarifies the remaining work, map it to existing criteria and accepted evidence; do not restart the project, reset counters or reopen unaffected acceptance. Keep ordinary repairs with their worker through focused tests. Prefer the existing manager conversation; create a replacement only for an evidenced continuity/capability failure, carrying state forward.

## Lessons from Astrid and Otto

These examples explain the reasoning, not permanent verdicts about those projects or instructions to modify their current runs.

- **Astrid: coordination around a real defect.** Lifecycle/cleanup proof can expose legitimate identity or authority failures. “Stop checking” would be the wrong correction. Select the actual repair, give one integration owner the connected implementation and proof, reuse existing broker mechanisms, and review only the affected delta. Repeated inventories, fragmented handoffs and reassurances do not fix that defect.
- **Otto: desired evidence becoming a new prerequisite.** A demand for telemetry a host does not emit can accidentally require a host redesign before the original task can run. Recover the actual acceptance need; use supported native observations plus explicitly labelled owner-side verification where sufficient and authorized. Keep the two sources of evidence distinct. Do not fabricate native output, waive a real guarantee or endlessly polish an unreachable proof route.
- **Both: choose the remaining path.** Separate accepted work, active useful work and concrete blockers. A real installed one-shot path often resolves more uncertainty than another broad plan or fixture-only success. Preserve unknown-attempt/no-retry safeguards and genuine review limits while removing agent-invented dependencies. Follow evidence of action and results, not declarations that instructions will be followed.

## Cadence, follow-up and low noise

Activation anchors checks at +1h and +3h, then +9h, +15h and every six hours thereafter. A manager can ask a question immediately; a one-time check uses the same path. A corrective message actually delivered to the manager creates a follow-up at delivery +1h. It never resets the baseline. Delivery uncertainty must be reconciled, not treated as success or blindly resent.

At follow-up, inspect adoption and effect. Useful work in progress is acceptable; one hour is not a completion deadline. If it is on course, retain the observation and return to baseline. If it is stalled, diagnose what prevents the selected action and provide a materially improved correction if needed. Do not issue the same instruction every hour. A new corrective instruction can justify its own follow-up; unchanged reminders cannot sustain an endless chain.

Use existing decision/issue/report identifiers and an inspected position to remember the concern, evidence, disposition, selected action and revisit condition. A watch/dismiss decision suppresses the same unchanged concern. Revisit when evidence materially changes, a relevant deadline/condition is reached, the chosen approach fails, or a genuinely resolved problem recurs. A clock expiry alone does not turn the old observation into new evidence. Superseded/resolved concerns remain historical context, not active nags. This does not require a new issues database or automated flag lifecycle.

Serialize checks and manager questions for one advisor through the same admission path; combine coincident reasons when one inspection covers them. After downtime, inspect current state once rather than replay every missed check. Finish, pause or withdrawal stops applicable timers; a blocked project still gets mandate-appropriate attention. Routine healthy/unchanged checks stay quiet to the owner. Meaningful outcomes, failures and actual owner decisions may warrant notification.

Scheduled advice is not an additional independent certification pass. Preserve adopted supervision allowances, review/oracle accounting and separation of duties. Never relabel a review as a check-in to bypass a cap, or charge the product's ongoing supervision to this build project's three-call oracle budget. Automating signal extraction can be considered later if observed volume justifies it; raw flags should inform the advisor's judgment, not automatically instruct managers.

## Intervene on the process itself

A reviewer checks the candidate against the adopted contract. The advisor also
asks whether the chosen procedure still serves the owner's outcome. It may
challenge the procedure without waiving a substantive requirement. Useful
bookkeeping preserves assignments, exact candidates, actual results, decisions,
verdicts and consumed or uncertain attempts. Those records do not automatically
become acceptance criteria or prerequisites for every subsequent operation.


When preparation creates the artifact that makes a later freshness check fail,
or every status update forces another signed packet, the repeated defect is in
the qualification procedure. Follow the connected transition: does an earlier
successful step create legitimate output that a later check rejects? Do not
answer with another demand for more checking.
Identify the intended product invariant, reconstruct the complete state transition,
and select the smallest simplification the mandate permits. One owner should
carry that repair through actual operation and observed outcome.

An advisor may remove an agent-invented requirement within delegated scope;
explicit owner acceptance, review/spending limits or execution boundaries require
an actual owner amendment. Preserve previous verdicts, consumed attempts and
uncertain effects. A changed procedural contract is not a retroactive PASS.
A bounded campaign may replace repeated per-attempt certification when authorized;
it never replaces current recipient, permission or idempotency checks.

Progress text and historical as-of status are not inputs that must match forever.
Actual adopted brief/mandate/policy and executable/data identities still are.
Keep this distinction in core binding and pack instructions. Do not turn the
advisor's own recommendations, reports or decision IDs into a growing prerequisite
chain for ordinary implementation. The advisor should measure whether its advice
reduced remaining work; if it only produced more machinery, revise the advice.

A terminal failed/unknown occurrence holds its dependent execution. Continue
useful authorized offline work, then prepare the precise missing decision if
needed. Never manufacture activity, repeat exhausted evidence searches, or stop
at a repair milestone while the next authorized action is ready.

## Prove the useful behavior economically

PA02/PA05 turn this playbook into adopted role instructions and templates. PA06 demonstrates one authentic manager/advisor conversation, native wake, meaningful correction and observed follow-up effect. Focused scenarios cover healthy silence, an invented prerequisite, a real defect, a repeated already-dispositioned concern, ongoing useful repair at follow-up and revision of mistaken advice. Combine these with existing tests and a small bounded fixture set; do not build an evaluation platform or add model-review stages.
